# เครดิตสมาชิก: หมดอายุวันเดียวทั้งกระปุก และเติมเงินคือการต่ออายุ

**วันที่:** 2026-08-11 · **สถานะ:** รออนุมัติ · **เดดไลน์:** ต้องขึ้นก่อน 12 ต.ค. 2026

## ปัญหา

`member_balances` เดิมคิดยอดคงเหลือแบบนี้:

```
คงเหลือ = ผลรวม credit_added ของก้อนที่ยังไม่หมดอายุ − ผลรวม credit_used ทุกบิลทุกยุค
```

สองข้างใช้เกณฑ์เวลาไม่เหมือนกัน พอก้อนหนึ่งหมดอายุ ยอดที่ให้จะหลุดจากสมการแต่ยอดที่ใช้ยังอยู่
ยอดใช้ของก้อนที่ตายแล้วจึงย้ายไปกัดกินก้อนที่ยังไม่หมดอายุ **ลูกค้าจะถูกริบเครดิตที่ยังใช้ได้จริง**

ยังไม่เคยเกิดขึ้น เพราะก้อนแรกสุดหมดอายุ **12 ต.ค. 2026** ตัวอย่างที่วัดได้: คุณพิมพ์ (0889469666)
ถือเครดิต 5,420฿ วันที่ 13 ต.ค. สูตรเดิมจะแสดง −580฿ และระบบจะจัดเธอเข้าช่อง "หมดแล้ว"

## ทำไมถึงทิ้งทางแก้เดิม (FIFO)

วันที่ 11 ส.ค. 2026 เราลองแก้ด้วยการจัดสรรยอดใช้ลงก้อนแบบ FIFO เรียงตามวันหมดอายุ
ขึ้น production ไปแล้วและ**พบว่าผิด** เพราะจัดสรรโดยไม่ดูวันที่ขาย บิลจึงไปดูดเครดิตจากก้อนที่
ตอนนั้นลูกค้ายังไม่ได้ซื้อ

หลักฐานจากข้อมูลจริง — **คุณตี๋ (0976866666)**: ถือก้อน Gold 12,000฿ เติม 17 เม.ย.
(หมด 17 เม.ย. 2027) และ Silver อีก 4 ก้อนที่เติมทีหลัง (มิ.ย.–ส.ค.) แต่หมดอายุก่อน (ธ.ค.–ก.พ.)
เขาใช้ไป **11,460฿ ในช่วงที่มีแต่ก้อน Gold** แต่ FIFO ตามวันหมดอายุยกยอดนั้นไปลง Silver
ทำให้ระบบคิดว่า Gold แทบไม่ถูกแตะ วันที่ 8 ก.พ. 2027 ระบบจะโชว์ 5,090฿ ทั้งที่ความจริงเหลือ 540฿

การแก้ให้ถูกต้องแบบ FIFO ต้องจัดสรรบิลเรียงตามวันขายลงเฉพาะก้อนที่มีชีวิตในวันนั้น ซึ่งต้องใช้
recursive CTE และมีทางผิดได้อีกหลายแบบ **เราเลือกเปลี่ยนกติกาธุรกิจแทน เพื่อให้คำถาม
"บิลนี้ตัดจากก้อนไหน" หมดความหมายไปเลย**

## กติกาใหม่

1. **เครดิตของลูกค้าหนึ่งคนคือกระปุกเดียว** ไม่แยกก้อน ไม่มีลำดับการใช้
2. **วันหมดอายุ = วันที่ไกลที่สุดในบรรดาก้อนที่ลูกค้ามี** เติมเงินครั้งใหม่ก็คิดวันหมดอายุจาก
   วันที่เติม + อายุแพ็กเกจ ตามเดิม แล้วเอาวันที่ไกลกว่าเป็นวันของทั้งกระปุก
   → **การเติมเงินจะต่ออายุยอดเก่าให้อัตโนมัติ และไม่มีวันทำให้อายุสั้นลง**
3. **หมดอายุแล้ว = ใช้ไม่ได้ แต่ไม่หายไป** ยอดยังอยู่ในระบบ แค่ถูกแช่แข็ง
4. **เติมเงินใหม่เมื่อไหร่ ทุกอย่างฟื้นทันที** ทั้งยอดเก่าและยอดใหม่ใช้ได้ถึงวันหมดอายุใหม่

ตรวจสอบกับเคสที่เคยพัง: เติม 6,000 (หมด 12 ต.ค.) ใช้ 4,000 → เหลือ 2,000 แช่แข็งไว้
วันที่ 20 ต.ค. เติมอีก 5,000 (แพ็ก 6 เดือน → 20 เม.ย.) → ใช้ได้ **7,000฿** ถึง 20 เม.ย.
(สูตรเดิมจะได้ 1,000฿ ซึ่งผิด)

## ข้อมูลที่เก็บไว้ ไม่ต้องเปลี่ยนอะไรเลย

`member_topups.expiry_date` ทุกวันนี้เก็บ `topup_date + อายุแพ็กเกจ` ต่อแถวอยู่แล้ว
(ตรวจแล้ว: Silver 183–184 วัน · Gold 365 วัน · เครดิตคงเหลือ 365 วัน)

กติกาใหม่แค่**ตีความต่างไป** — เอา `MAX(expiry_date)` แทนการกรองรายก้อน
ข้อดีคือ **กันชน "ห้ามสั้นลง" ได้มาฟรี** เพราะ MAX ของเซ็ตที่มีแต่โตขึ้น ไม่มีทางลดลงเอง
คุณตี๋จึงยังได้ 17 เม.ย. 2027 ตามเดิม ไม่เสีย 68 วัน

**ไม่มี migration ที่ต้องแก้ข้อมูลย้อนหลัง ไม่มี backfill**

## นิยาม view ใหม่

```
credit_balance  = SUM(credit_added ทุกก้อน) − SUM(credit_used ทุกบิล)   ← ไม่กรองวันหมดอายุ
credit_granted  = SUM(credit_added ทุกก้อน)
bonus_granted   = SUM(bonus_added ทุกก้อน)
cash_paid       = SUM(cash_received ทุกก้อน)
next_expiry     = MAX(expiry_date)
credit_expired  = (next_expiry IS NULL OR วันนี้ > next_expiry)         ← คอลัมน์ใหม่
```

`next_expiry` เป็น NULL เมื่อลูกค้าไม่เคยเติมเงินเลย กรณีนั้นต้องนับเป็น "ใช้ไม่ได้" ไม่ใช่ NULL
ไม่งั้นเงื่อนไขกันการจ่ายจะกลายเป็น NULL แล้วหลุดผ่านไปเงียบ ๆ

- คอลัมน์เดิมทั้ง 11 ตัวคงชื่อ ลำดับ และชนิดเดิมทุกประการ `credit_expired` ต่อท้ายเป็นตัวที่ 12
- `credit_granted` / `bonus_granted` / `cash_paid` ต้องเลิกกรองวันหมดอายุด้วย เพื่อให้อยู่บนกระปุก
  เดียวกับ `credit_balance` — สำคัญเพราะ `memberRatio = cash_paid / credit_granted` ใช้ตัดสิน
  ว่าเงินที่ตัดเป็นรายได้เท่าไหร่ ถ้าตัวเศษกับตัวส่วนคนละขอบเขตจะคิดรายได้ผิด
- `next_expiry` เปลี่ยนความหมายจาก "ก้อนที่จะหมดก่อน" เป็น "วันหมดอายุของทั้งกระปุก"
  ซึ่งตรงกับที่หน้าจอสื่อกับลูกค้าอยู่แล้ว
- ต้องมี `with (security_invoker = true)` และใช้ `(now() at time zone 'Asia/Bangkok')::date`

**ผลพลอยได้:** ยอดติดลบจะกลับมาเป็นสัญญาณที่มีความหมายอีกครั้ง เพราะถ้าบิลถูกคีย์ใส่ลูกค้าที่
ไม่เคยเติมเงิน ยอดจะติดลบทันที (เคส "เดียร์" 1,300฿ เมื่อเช้านี้) การตรวจ `negative_credit`
กับ `orphan_credit_used` ที่มีอยู่จึงยังใช้ได้และเทียบเท่ากันพอดี

## การบังคับที่ฝั่ง server — จุดที่ห้ามพลาด

**ทุกวันนี้โค้ดจุดจ่ายเงินไม่ได้เช็ควันหมดอายุเลยแม้แต่บรรทัดเดียว** เพราะ view คัดก้อนที่หมดอายุ
ออกให้เงียบ ๆ อยู่แล้ว การกันจึงซ่อนอยู่ในตัวเลข ไม่ได้อยู่ในโค้ด

พอ `credit_balance` รวมเครดิตแช่แข็งเข้ามา **ถ้าไม่เติมการเช็คเข้าไป เครดิตที่หมดอายุจะใช้ได้ทันที
ทั้งก้อน** ขนาดของความเสี่ยง: เครดิตค้างในระบบราว 160,000฿ (ขยับทุกวันตามการขาย)
และสมาชิก 39 คนมีของที่จะหมดอายุภายในปีนี้

ต้องเพิ่มการเช็คที่ทั้งสองทางเข้า และต้องเป็นฝั่ง server ไม่ใช่แค่ทำปุ่มเป็นสีเทา:

- `src/app/(app)/sale-actions.ts` ราวบรรทัด 163–185 (`createSale`)
- `src/app/(app)/sale-actions.ts` ราวบรรทัด 650–665 (`updateSale`)

ข้อความที่ปฏิเสธต้องบอกทางออกให้พนักงานพูดต่อได้ทันที เช่น
*"เครดิตหมดอายุเมื่อ 12 ต.ค. 2026 — เติมแพ็กเกจใหม่แล้วใช้ยอดเดิม 2,000 บาทได้ทันที"*

## หน้าจอ

**ห้ามซ่อนเครดิตที่แช่แข็ง** เพราะมันคือจังหวะขายที่ดีที่สุดที่กติกานี้สร้างให้
พนักงานควรพูดได้ว่า *"คุณมีเครดิตค้าง 2,000 บาทนะคะ เติมวันนี้อีก 5,000 ใช้ได้ทั้ง 7,000 เลยค่ะ"*

- หน้าลูกค้า (`customers/[id]`) และตารางลูกค้า: โชว์ยอดตามปกติ + ป้าย "หมดอายุแล้ว — เติมเพิ่มเพื่อปลดล็อก"
- หน้า POS (`customer-picker`, `group-pos-form`): โชว์ยอดพร้อมป้าย และปิดปุ่มจ่ายด้วยเครดิต
- หน้าสมาชิก (`members`): ลูกค้าที่หมดอายุยังต้องอยู่ในรายการ ไม่ใช่หายไป เพราะเป็นกลุ่มเป้าหมายให้ตามกลับ
- `creditBucket()` ใน `src/lib/member-credit.ts`: เพิ่มสถานะ `expired` แยกจาก `empty`
  — "มีเครดิตแต่ใช้ไม่ได้" กับ "ไม่มีเครดิต" เป็นคนละเรื่องและต้องสื่อสารต่างกัน

## เกณฑ์ตรวจรับ

**ห้ามใช้เกณฑ์ "ผลลัพธ์เท่าเดิมทุกคนวันนี้" เป็นตัวตัดสิน** — บทเรียนจากรอบที่แล้ว เกณฑ์นั้น
พิสูจน์อะไรไม่ได้เลยเพราะยังไม่มีก้อนไหนหมดอายุ ทุกสูตรจึงยุบเหลือ `เติม − ใช้` เหมือนกันหมด
มันพิสูจน์แค่ว่าวันนี้ไม่พัง ไม่ได้พิสูจน์ว่าสิ่งที่ตั้งใจแก้ทำงานถูก

ต้องผ่านทุกข้อ โดยจำลองวันที่ในการทดสอบ:

1. **คุณตี๋ยังได้วันที่ยาวกว่า** — `next_expiry` = 2027-04-17 ไม่ใช่ 2027-02-08
2. **แช่แข็งแล้วยอดไม่หาย** — จำลองวันที่ 2026-10-13 ลูกค้าที่ก้อนหมดอายุต้องยัง
   `credit_balance` เท่าเดิม และ `credit_expired = true`
3. **เติมแล้วฟื้น** — จำลองการเติมหลังหมดอายุ ยอดต้องเป็น (ยอดเก่า + ยอดใหม่) และใช้ได้
4. **server ปฏิเสธจริง** — เรียก `createSale` ด้วย Member Credit ให้ลูกค้าที่หมดอายุ ต้องถูกปฏิเสธ
   พร้อมข้อความที่บอกทางออก และต้องปฏิเสธที่ `updateSale` ด้วย
5. **บิลคีย์ผิดใบยังจับได้** — ลูกค้าที่ไม่เคยเติมแต่มีบิลตัดเครดิต ต้องได้ยอดติดลบและติดธง
6. `reconciliation.sql` PASS ทุกข้อ (ยกเว้น `bed_double_booked` ที่ FAIL อยู่ก่อนแล้วจากคิวซ้อน 9 ส.ค.)
7. เทสต์เดิม 592 ตัวผ่าน + เทสต์ใหม่ของ `creditBucket()` สถานะ `expired`

## ผลกระทบทางบัญชีที่ตกลงกันแล้ว

เมื่อเครดิตไม่มีวันหายไปเอง **ภาระให้บริการจะค้างในบัญชีตลอดกาล** เหตุการณ์ "เครดิตหมดอายุ
แล้วตกเป็นรายได้ร้าน" จะไม่เกิดขึ้นอีก — ยอมรับได้ และดีกว่าในแง่ความสัมพันธ์กับลูกค้า

ถ้าวันหนึ่งอยากตัดจำหน่ายบัญชีที่ตายจริง (เช่น เงียบเกิน 2 ปี) ให้ทำเป็น**ปุ่มที่คนกดพร้อมเหตุผล**
ไม่ใช่ผลข้างเคียงเงียบ ๆ ของวันที่ผ่านไป — ไม่ทำรอบนี้

## สิ่งที่ไม่ทำรอบนี้

- ปุ่มตัดจำหน่ายเครดิตที่ตายแล้ว
- แจ้งเตือนใน Daily Report ว่ามีสมาชิกกี่คนเครดิตหมดอายุ (ทำทีหลังได้ ไม่กระทบสูตร)
- แคมเปญตามลูกค้าที่เครดิตแช่แข็งให้กลับมาเติม (เป็นงานการตลาด ไม่ใช่งานระบบ)
