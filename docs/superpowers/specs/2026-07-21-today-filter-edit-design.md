# SOOKKAYA POS — หน้ายอดขายแบบเลือกวันได้ และแก้ไขรายการขาย

วันที่: 2026-07-21
สถานะ: รออนุมัติ

## ที่มา

หน้า `/today` แสดงยอดขายของ "วันนี้" อย่างเดียว ดูย้อนหลังไม่ได้ และแก้รายการที่บันทึกผิดไม่ได้
ทำได้แค่ลบทิ้งแล้วบันทึกใหม่ ซึ่งทำให้เลขใบเสร็จเดินและเวลาขายเพี้ยน

## ขอบเขต

1. เลือกวันที่และช่วงวันได้ · ค่าเริ่มต้นคือวันนี้ตามเวลาไทย
2. แสดงรายละเอียดรายการขายให้ครบทุกช่องที่บันทึกไว้
3. แก้ไขรายการขายได้
4. ลบได้ (มีอยู่แล้ว)

**นอกขอบเขต:** แก้รายการของเดือนก่อนหน้า · แก้ยอดเติมเงินสมาชิก · แก้รายจ่าย · ประวัติการแก้ไข (audit log)

## การตัดสินใจที่เคาะแล้ว

| เรื่อง | เลือก |
| ------ | ----- |
| ช่วงวัน | อยู่ในหน้าเดียวกับรายวัน ไม่แยกไปหน้า `/sales` |
| ขอบเขตการแก้ | ทุกช่อง รวมรายการที่จ่ายด้วย Member Credit (ต้องคำนวณเครดิตใหม่ทุกครั้ง) |
| ย้อนหลัง | แก้/ลบได้เฉพาะ**เดือนปัจจุบัน** เดือนก่อนหน้าดูได้อย่างเดียว |
| เครดิตคงเหลือ | แสดง**ยอดปัจจุบัน**ไม่ใช่ยอด ณ วันที่ขาย |

**ทำไมไม่แสดงเครดิต ณ วันที่ขาย:** ต้องไล่ย้อน topup กับการใช้ทั้งหมดก่อนหน้านั้น
ได้ตัวเลขที่ถูกแต่เอาไปตัดสินใจอะไรไม่ได้ สิ่งที่คนกดแก้ต้องรู้คือ
"แก้ยอดขึ้นได้อีกกี่บาทโดยไม่ติดลบ" ซึ่งตอบด้วยยอดปัจจุบันเท่านั้น

## สถาปัตยกรรม

### ปัญหาที่ต้องแก้ก่อน — สูตรเงินจะถูกเขียนสองที่

`createSale` ใน `src/app/(app)/sale-actions.ts` คำนวณ 4 อย่างที่ผูกกันแน่น:
ยอดสุทธิ · ค่ามือ · เครดิตที่ตัด · รายได้ที่รับรู้ ถ้า `updateSale` เขียนสูตรชุดเดียวกันซ้ำ
สองเส้นทางจะค่อยๆ ห่างกัน แล้วยอดที่ได้จาก "บันทึกใหม่" กับ "แก้ของเดิม" จะไม่ตรงกัน
ซึ่งเป็นรูปแบบเดียวกับบั๊กเรื่องเงิน 4 จุดที่โปรเจกต์นี้เจอมาแล้ว (กฎบัญชีข้อ 3)

**ทางแก้:** แยกสูตรออกมาเป็นฟังก์ชันบริสุทธิ์ `src/lib/sale-math.ts` ที่มีเทส
แล้วให้ `createSale` และ `updateSale` เรียกตัวเดียวกัน

```ts
computeSaleAmounts({
  priceNormal, discount, paymentMethod, gowabiNet,
  isRequest, requestFee, serviceCommission,
  memberRatio,           // cash_paid / credit_granted · null เมื่อไม่ใช่สมาชิก
}) => { netAmount, discount, commission, requestFee, creditUsed, bonusUsed, revenueRecognize }
```

`createSale` ต้องเปลี่ยนมาใช้ตัวนี้ด้วย และตัวเลขที่ได้ต้องเท่าเดิมทุกบาท —
พิสูจน์ด้วยการรัน reconciliation หลังแก้

### เครดิตสมาชิกตอนแก้ไข

รายการเดิมตัดเครดิตไปแล้ว `credit_used` บาท ยอดที่แก้ได้สูงสุดคือ
`เครดิตคงเหลือปัจจุบัน + credit_used ของรายการนี้` เพราะการแก้จะคืนของเดิมแล้วตัดใหม่

**เรื่องที่ต้องบอกผู้ใช้ให้เห็น:** สัดส่วนรับรู้รายได้ (`cash_paid / credit_granted`)
คำนวณจากสถานะสมาชิก ณ ตอนที่กดแก้ ถ้าลูกค้าเติมเงินเพิ่มหลังจากวันที่ขาย
สัดส่วนจะไม่เท่าตอนบันทึกครั้งแรก หน้าจอต้องแสดงว่ารายได้รับรู้เปลี่ยนจากเท่าไหร่เป็นเท่าไหร่
ห้ามเปลี่ยนเงียบๆ

### เส้นทางและพารามิเตอร์

`/today?from=YYYY-MM-DD&to=YYYY-MM-DD`
ไม่ใส่ = วันนี้ทั้งคู่ · `from` เท่ากับ `to` = โหมดวันเดียว · ต่างกัน = โหมดช่วงวัน

ปุ่มควบคุม: `←` `→` เลื่อนทีละวัน (โหมดช่วงเลื่อนทั้งหน้าต่าง) · ช่องเลือกวันที่สองช่อง ·
ปุ่มลัด "วันนี้" "7 วันล่าสุด" "เดือนนี้"

โหมดช่วงวันจัดกลุ่มตามวัน มีหัววันและยอดรวมของวันนั้น เพื่อไม่ให้กดแก้ผิดวัน

## การทดสอบ

`sale-math.ts` เป็นฟังก์ชันบริสุทธิ์ เขียนเทสก่อน เคสที่ต้องมี:

- ขายปกติ — ยอดสุทธิ = ราคา − ส่วนลด
- Gowabi — ยอดรับจริงกรอกเอง ส่วนลดคือส่วนต่างจากราคาปกติ
- Member Credit — ตัดเครดิตเต็มยอด แยกส่วนที่เป็นของแถมออกจากรายได้รับรู้
  (Silver จ่าย 5,000 ได้ 6,000 → ใช้ 690 รับรู้ 575 ของแถม 115)
- สัดส่วนสมาชิกเป็น null → รับรู้เต็มจำนวน
- ส่วนลดมากกว่าราคา → ยอดติดลบ ต้องถูกปฏิเสธ
- ค่ารีเควสไม่ถูกนับรวมในยอดขาย แต่บวกเข้าค่ามือหมอ

หลังแก้ `createSale` ให้ใช้ `sale-math` ต้องรัน `supabase/reconciliation.sql` (21 ข้อ)
ให้ PASS ครบ เพื่อพิสูจน์ว่าตัวเลขเดิมไม่ขยับ
