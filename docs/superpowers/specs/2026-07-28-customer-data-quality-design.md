# ป้ายบอกปัญหาข้อมูลลูกค้า + ตารางรายชื่อ — Design

**วันที่:** 28/7/2569
**สถานะ:** อนุมัติแล้ว (เจ้าของร้าน 28/7/2569)

## เป้าหมาย

ทำให้เห็นด้วยตาทันทีว่าลูกค้าคนไหนมีข้อมูลที่ทำให้ระบบทำงานผิด และกรองดูทีละกลุ่มได้
เพื่อให้พนักงานหน้าร้านไล่ตรวจได้ พร้อมเปลี่ยนรายชื่อจากการ์ดเป็นตารางที่อ่านทีละแถวได้

## ที่มา

ตรวจข้ามระบบ 28/7/2569 พบว่าลูกค้า 1,046 คนมีปัญหาซ่อนอยู่ 156 ระเบียน โดยไม่มีอะไรในระบบบอก
เคสที่ทำให้เห็นปัญหาชัดที่สุดคือ "กล้วย/สงกรานต์" — คนเดียวกันแตกเป็นสองระเบียน
แพ็กเงินไปอยู่ระเบียนหนึ่ง บิลไปลงอีกระเบียน เครดิตเลยติดลบ 2,380 โดยไม่มีใครรู้จนกว่าจะไปขุด

## ขอบเขต

**ทำ**
- ป้ายบอกปัญหา 5 แบบบนรายชื่อลูกค้า
- แถวชิพกดกรองทีละปัญหา พร้อมตัวเลขกำกับ
- เปลี่ยนรายชื่อเป็นตารางบนคอม/แท็บเล็ต · การ์ดบนมือถือ

**ไม่ทำ (ตัดสินใจแล้ว)**
- ปุ่มรวมลูกค้าซ้ำในตาราง — เจ้าของร้านสั่งให้พนักงานตรวจก่อน การรวมยังใช้ปุ่มเดิมในหน้าโปรไฟล์
- ป้ายเหล่านี้ในหน้า POS / ช่องค้นหาลูกค้า — คนละงาน ไว้ค่อยพิจารณา
- ป้าย "ยังไม่เคยมาสักครั้ง" (129 คน) — ส่วนใหญ่คือคนที่เพิ่งลงทะเบียนไลน์หรือเพิ่งถูกเพิ่ม ไม่ใช่ข้อมูลผิด
- ป้าย "ชื่ออ่านไม่ออก" (2 คน) — ไม่กระทบการทำงาน

## กติกา: อะไรคือปัญหา

แบ่งสองกลุ่มตามความหมาย และให้สีต่างกันเพื่อให้แยกออกด้วยตา

### กลุ่มตัวตน (สีเหลือง) — ระบบระบุตัวลูกค้าผิดคนได้

| ป้าย | เงื่อนไข | ผลเสีย | ตอนนี้ |
|---|---|---|---|
| เบอร์ซ้ำ | มีลูกค้าคนอื่นที่ `phone` เท่ากัน | บิล/แต้ม/เครดิตอาจไปลงผิดคน | 64 |
| ไม่มีเบอร์ | `phone` เป็น null หรือ `''` | ผูกแต้มไม่ได้ · ครั้งหน้ามาจะกลายเป็นคนใหม่ | 73 |
| เบอร์ผิดรูป | `phone` ไม่ตรง `^0[0-9]{8,9}$` | ค้นไม่เจอ เท่ากับไม่มีเบอร์ | 18 |

"ไม่มีเบอร์" กับ "เบอร์ผิดรูป" ไม่มีทางเกิดพร้อมกัน (เงื่อนไขตัดกันเอง)
ส่วน "เบอร์ซ้ำ" เกิดพร้อม "เบอร์ผิดรูป" ได้ เช่น โอ/โอ๋ ที่ใช้เบอร์ `611230256` เหมือนกันและขาดเลข 0 หน้า

### กลุ่มเงิน (สีแดง) — ตัวเลขเงินไม่ตรง

| ป้าย | เงื่อนไข | ตอนนี้ |
|---|---|---|
| เครดิตติดลบ | `credit_balance < 0` | 1 |
| แต้มติดลบ | แต้มคงเหลือ `< 0` | 0 |

## สถาปัตยกรรม

### View `v_customer_issues`

คำนวณธงทั้งห้าใน SQL **ไม่ใช่ในหน้าเว็บ** เพราะ PostgREST คืนสูงสุด 1,000 แถว
แต่ลูกค้ามี 1,046 คนแล้ว ถ้าดึงมากรองในหน้าเว็บ คนที่เรียงท้ายสุดจะหายเงียบและตัวเลขจะต่ำกว่าจริง
(กับดักเดียวกับที่หน้าสมาชิกเคยเจอ ดูคอมเมนต์ใน `members/page.tsx`)

```sql
create view public.v_customer_issues with (security_invoker = true) as
select
  c.id                                   as customer_id,
  c.name,
  c.nickname,
  c.phone,
  c.customer_type,
  coalesce(mb.credit_balance, 0)         as credit_balance,
  coalesce(ltv.visits, 0)                as visits,
  ltv.last_visit,
  -- ธงปัญหา — ที่เดียวที่ตัดสินว่าอะไรคือปัญหา
  (c.phone is not null and c.phone <> ''
     and exists (select 1 from public.customers o
                  where o.id <> c.id and o.phone = c.phone))          as dup_phone,
  (c.phone is null or c.phone = '')                                    as no_phone,
  (c.phone is not null and c.phone <> ''
     and c.phone !~ '^0[0-9]{8,9}$')                                   as bad_phone,
  (coalesce(mb.credit_balance, 0) < 0)                                 as negative_credit,
  (coalesce(pb.balance, 0) < 0)                                        as negative_points
from public.customers c
left join public.member_balances  mb  on mb.customer_id  = c.id
left join public.v_customer_ltv   ltv on ltv.customer_id = c.id
left join public.v_point_balances pb  on pb.customer_id  = c.id;
```

`security_invoker = true` บังคับตาม RLS ของผู้เรียก — ห้ามลืม ชุดตรวจ `views_without_security_invoker`
จะ FAIL ทันทีถ้าหลุด (เคยหลุดมาแล้วตอน `create or replace view` ล้าง reloptions ทิ้ง)

### `src/lib/customer-issues.ts`

ที่เดียวของความจริงเรื่อง **ป้าย** — ชื่อที่แสดง สี ลำดับ และชื่อคอลัมน์ใน view

```ts
export type IssueKey =
  | "dup_phone" | "no_phone" | "bad_phone" | "negative_credit" | "negative_points"

export type IssueTone = "identity" | "money"

export type IssueDef = {
  key: IssueKey
  label: string
  tone: IssueTone
  /** อธิบายว่าทำไมถึงเป็นปัญหา — ใช้ใน tooltip ของชิพ */
  why: string
}

export const ISSUES: IssueDef[] = [ /* เรียงตามลำดับที่จะโชว์บนแถวชิพ */ ]

/** แถวจาก v_customer_issues → รายการปัญหาที่ต้องติดป้าย (เรียงตาม ISSUES) */
export function issuesOf(row: Partial<Record<IssueKey, boolean | null>>): IssueDef[]

/** คลาส Tailwind ของป้ายตามกลุ่ม — เหลือง=ตัวตน แดง=เงิน */
export function issueBadgeClass(tone: IssueTone): string
```

ห้ามใส่ `"use client"` — หน้าที่เรียกเป็น server component

### `src/app/(app)/customers/page.tsx`

- อ่านจาก `v_customer_issues` แทน `member_balances`
- `searchParams` เพิ่ม `issue` (ค่าเป็น `IssueKey` ตัวใดตัวหนึ่ง หรือว่าง)
  **กดได้ทีละปัญหา** — กดชิพใหม่ทับของเดิม กดชิพเดิมซ้ำคือยกเลิกกรอง
  (ไม่ทำหลายเงื่อนไขพร้อมกัน เพราะงานจริงคือไล่ตรวจทีละกลุ่ม)
- นับจำนวนของทุกชิพด้วย `head: true` ทีละธง (5 คำสั่ง เบา ไม่ดึงแถวจริง)
- กรอง: `.eq(issue, true)` เมื่อมี `issue`
- **เรียงพิเศษเมื่อกรอง `dup_phone`: บังคับเรียงตาม `phone`** เพื่อให้คู่เดียวกันอยู่ติดกัน
  ถ้าเรียงตามชื่อ "แมน" กับ "พี พีรดา" จะอยู่คนละหน้ากันจนตรวจไม่ได้
- แบ่งหน้า 50 คนต่อหน้าด้วย `.range()` + `PagerLink` ที่มีอยู่แล้ว
  และเขียนจำนวนจริงเสมอ "แสดง 1–50 จาก 64 คน" — ห้ามตัดเงียบ

### `src/app/(app)/customers/customer-table.tsx` (ใหม่)

รับแถวที่ query มาแล้ว แสดงสองแบบด้วย CSS ไม่ใช่ JS (server component ล้วน)

- `hidden sm:table` — ตาราง 7 คอลัมน์: ชื่อ · เบอร์โทร · ประเภท · เครดิต · มาแล้ว · มาล่าสุด · สถานะข้อมูล
- `sm:hidden` — การ์ดเรียงลง โดยยกป้ายสถานะข้อมูลไว้ใต้ชื่อ

หัวคอลัมน์ที่เรียงได้เป็นลิงก์ `?sort=` ธรรมดา (ไม่ต้องมี JS ฝั่งไคลเอนต์)
เรียงได้: ชื่อ · เบอร์ · เครดิต · จำนวนครั้ง · มาล่าสุด

แถบพื้นหลังอ่อนสลับทีละกลุ่มเบอร์ **เฉพาะตอนกรอง `dup_phone` เท่านั้น**
(กรณีอื่นแถวไม่ได้เรียงตามเบอร์ แถบสีจะกลายเป็นลายมั่วที่ไม่มีความหมาย)
คำนวณจากจุดที่ค่าเบอร์เปลี่ยนระหว่างไล่แถว ไม่ต้องเก็บ state

## ความเสี่ยงที่รู้ตัว

- **หน้านี้ยิงเพิ่มอีก 5 query สำหรับนับเลขบนชิพ** — ทั้งหมดเป็น `head: true` ไม่ดึงแถว ควรเร็ว
  ถ้าช้าจริงค่อยยุบเป็น query เดียวที่ `sum(case when …)` ทีหลัง
- **`dup_phone` เป็น correlated subquery** บน 1,046 แถว — เร็วพอในขนาดนี้
  ถ้าลูกค้าโตถึงหลักหมื่นค่อยเปลี่ยนเป็น window function
