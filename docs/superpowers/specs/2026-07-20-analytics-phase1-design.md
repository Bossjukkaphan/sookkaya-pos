# SOOKKAYA POS — รายงานย้อนหลังและการวิเคราะห์ (เฟส 1)

วันที่: 2026-07-20
สถานะ: อนุมัติแล้ว รอเขียนแผนลงมือ

## ปัญหาที่แก้

ระบบปัจจุบันดูข้อมูลได้แค่ "วันนี้" (หน้ายอดขาย, หน้าค่ามือ) และ "เดือนนี้" (หน้ารายงาน)
ยังทำสิ่งที่เจ้าของร้านเคยทำได้ใน Excel ไม่ได้:

- เลือกช่วงเวลาเองแล้วดูยอดขาย
- ดูสรุปค่ามือหมอข้ามหลายวันในหน้าเดียว
- แยกกระแสเงินสดออกจากรายได้ที่รับรู้
- วิเคราะห์จุดคุ้มทุน กำไรต่อเมนู ความหนาแน่นการจอง

เป้าหมายคือยกฟีเจอร์จาก dashboard เดิม (`sookkaya-dashboard/index.html` — 6 หมวด:
cockpit / today / finance / team / members / analytics) เข้ามาในระบบ POS
โดยใช้ฐานข้อมูลเดียวกัน ไม่ต้องพึ่ง Google Sheets อีก

## การแบ่งเฟส

งานทั้งหมดใหญ่เกินกว่าจะเป็น spec เดียว จึงแบ่ง 3 เฟส แต่ละเฟสใช้งานได้ด้วยตัวเอง

| เฟส | ได้อะไร | สถานะ |
| --- | ------- | ----- |
| **1** | รากฐาน (แก้ข้อมูล + views) · ดูย้อนหลังตามช่วงเวลา · สรุปค่ามือข้ามวัน | **spec นี้** |
| 2 | P&L รายเดือน · กระแสเงินสด vs net revenue · จุดคุ้มทุน · หน้าตั้งค่าจัดกลุ่มต้นทุน | รอ |
| 3 | Heatmap ชั่วโมง×วัน · กำไรต่อเมนู · ROI ส่วนลด · LTV สมาชิก · ลูกค้าที่หายไป | รอ |

เฟส 1 มาก่อนเพราะเป็นตัวปลดล็อก — เฟส 2 ต้องใช้การจัดประเภทต้นทุน
และเฟส 3 ต้องใช้เวลาขายกับต้นทุนวัสดุ ซึ่งทั้งหมดเกิดในเฟส 1

การกู้เวลาขายต้องทำทันที ไม่รอเฟส 3 เพราะทุกวันที่ผ่านไปมีการบันทึกขายใหม่
ยิ่งช้ายิ่งต้องแก้ข้อมูลปนกันระหว่างของเก่ากับของใหม่

## ข้อตกลงที่ตัดสินแล้ว

### 1. นิยามกำไร — แสดงทั้งสองตัว ยึด Excel เป็นหลัก

Excel เดิมกับหน้ารายงานปัจจุบันให้กำไรเดือน มิ.ย. ต่างกัน 25,153 บาท
ส่วนต่างมาจาก 2 จุดพอดี:

| จุด | ส่วนต่าง |
| --- | -------- |
| รายได้: ยอดขายรวม − ยอดที่รับรู้ (ส่วนโบนัสสมาชิกที่ไม่ใช่เงินจริง) | 14,318 |
| ค่ามือ: ที่จ่ายจริงในเดือน (151,250) − ที่เกิดขึ้นจากงานในเดือน (140,415) | 10,835 |

กำไรเชิงบัญชี มิ.ย. ที่ถูกต้อง = 88,991 + 25,153 = **114,144**

**ตัดสิน:** แสดงทั้ง *เงินสดจริง* (สูตร Excel) และ *กำไรเชิงบัญชี* คู่กัน
โดย **Net Revenue = ยอดที่รับรู้เสมอ** (ตัดส่วนโบนัสสมาชิกออก)

ค่านี้มีอยู่แล้วในคอลัมน์ `sales.revenue_recognize` ซึ่ง import มาครบทุกแถว ไม่ต้องคำนวณย้อนหลัง

### 2. การจัดประเภทต้นทุน

| ประเภท | หมวดหมู่ |
| ------ | -------- |
| **fixed** | ค่าเช่าสถานที่ · ค่าน้ำ/ค่าไฟ/Internet · เงินเดือน reception · ค่าทำบัญชี |
| **variable** | ค่ามือหมอ · เงินเบิกล่วงหน้า · วัสดุ-สิ้นเปลือง · ซักรีด |
| **onetime** | การตลาด/โฆษณา · ชุดลูกค้า/หมอ/พนักงาน · อื่นๆ |

ยืนยันกับเจ้าของร้านแล้ว:

- **ซักรีด = variable** (ลูกค้าเยอะ = ผ้าเยอะ)
- **การตลาด = onetime** — แต่ละเดือนใช้ไม่เท่ากัน ขึ้นกับรูปแบบแคมเปญ
- **HR/payroll ปนกัน** — มีทั้งค่ามือหมอ ค่าประกัน **และเงินเดือนพนักงานต้อนรับ/แม่บ้าน**
  ต้องแยกตามชื่อรายการ ไม่ใช่เหมาทั้งหมวด
- **เงินเบิกล่วงหน้า ไม่ได้นับซ้ำ** — จ่ายก่อนแล้วหักออกจากรอบถัดไป
  เงินสดที่จ่ายจริงรวมกันได้ยอดค่ามือที่ถูกต้อง

ผลกระทบของการแยกเงินเดือนออกมา (มิ.ย. 69):

| | เหมาว่า HR เป็นค่ามือล้วน | แยกเงินเดือนออก |
| --- | --- | --- |
| ต้นทุนคงที่ | 52,198 | **104,648** |
| กำไรต่อเซสชัน | ฿320 | **฿420** |
| จุดคุ้มทุน | 164 เซสชัน | **250 เซสชัน** |

ตรวจแล้วบวกกลับได้ 258,027 เท่ากับ "รวมรายจ่ายทั้งหมด" ใน Excel

### 4. สถาปัตยกรรม — สูตรอยู่ในฐานข้อมูล

**เหตุผล:** โปรเจกต์นี้เจอบั๊กเรื่องเงินมาแล้ว 3 จุด และทุกจุดเกิดจากสาเหตุเดียวกัน —
นิยามถูกเขียนไว้ที่หนึ่ง แล้วอีกที่ไม่รู้

| บั๊กที่เคยเจอ | สาเหตุ |
| ------------- | ------ |
| โบนัสสมาชิกนับซ้ำ 53,000 บาท | view คิดอย่างหนึ่ง หน้าจอคิดอีกอย่าง |
| ค่ามือนับซ้ำในรายงานรายเดือน | หน้ารายงานไม่รู้ว่า HR/payroll คือค่ามือ |
| ประกันมือจ่ายให้หมอที่ไม่เข้างาน | หน้าค่ามือรายวันมีเงื่อนไข หน้ารายงานไม่มี |

เฟส 2–3 จะเพิ่มหน้าที่ใช้สูตรเดียวกันอีกหลายหน้า ถ้าไม่รวมสูตรก่อน บั๊กแบบนี้จะเกิดอีก

**วิธี:** Postgres รวมยอด (นิยามเดียว เร็ว) · TypeScript แสดงผลและกรอง (แก้ง่าย) ·
การจัดกลุ่ม fixed/variable เก็บเป็น**ข้อมูลในตาราง ไม่ฝังในโค้ด** แก้ได้โดยไม่ต้อง deploy

## การเปลี่ยนแปลงฐานข้อมูล

```sql
-- 1. จัดประเภทต้นทุน
alter table expenses add column cost_type text not null default 'variable'
  check (cost_type in ('fixed','variable','onetime'));

create table expense_category_types (
  category  text primary key,
  cost_type text not null check (cost_type in ('fixed','variable','onetime'))
);

-- 2. ต้นทุนวัสดุต่อเมนู
alter table services add column material_cost numeric;

-- 3. เป้ารายเดือน
-- settings: monthly_target = 400000
```

### Backfill รายจ่าย 169 รายการ

กฎ 2 ชั้น:

1. ตามหมวดหมู่ตามตารางข้างบน
2. **หมวด HR/payroll แยกตามชื่อรายการ** — มีคำว่า `reception` / `รีเซฟชั่น` / `บัญชี`
   → `fixed` ที่เหลือ → `variable`

ชื่อรายการเขียนไม่สม่ำเสมอ (`reception apr 26`, `เงินเดือนรีเซฟชั่น`,
`เงินเดือนพนักงาน reception`) การเดาจึงอาจพลาด → **ต้องให้เจ้าของร้านตรวจ
28 รายการในหมวด HR ก่อนปิดงาน** ห้ามปล่อยผ่านเงียบ เพราะกระทบจุดคุ้มทุนโดยตรง

### กู้เวลาขาย

ปัจจุบันมีเวลาแค่ 6 จาก 2,255 รายการ เพราะตอน import ทิ้งค่าที่รูปแบบกำกวม
ถอดรหัสได้แล้วว่าเป็นรูปแบบ `ชั่วโมง.นาที`:

| ในไฟล์ | ความหมาย | จำนวน |
| ------ | -------- | ----- |
| `10.05`, `10.3` | 10:05, 10:30 (ทศนิยมเติมศูนย์ขวาเป็นนาที) | 1,581 |
| `4.20pm` | 16:20 | 5 |
| `1515` | 15:15 | 1 |
| ค่าเศษส่วน Excel | แปลงตรงๆ | 2 |
| ตีความไม่ได้ (เศษ > .59) | ปล่อยว่าง | 1 |

รวมกู้ได้ **~1,589 รายการ** จับคู่ด้วย `receipt_no` (unique เก็บเลขเดิมไว้ครบ)
**แก้เฉพาะแถวที่ `sale_time` ว่าง** ถ้าจำนวนแถวที่แก้ผิดไปจากที่คาดมาก ให้หยุดและตรวจสอบ

## SQL Views

### หลักการบังคับ: view เก็บรายวัน แอปบวกรวมทีหลัง

ประกันมือ ฿500 เป็นกฎ**รายวันต่อคน** ถ้ารวมยอดทั้งช่วงก่อนแล้วค่อยเทียบประกัน จะผิดทันที

| | ค่ามือจริง | ผลลัพธ์ |
| --- | --- | --- |
| รัน วันจันทร์ | 150 | ได้ประกัน 500 |
| รัน วันอังคาร | 900 | ได้จริง 900 |
| **ถูก** (คิดรายวันแล้วบวก) | | **1,400** |
| **ผิด** (บวกก่อนแล้วเทียบ) | 1,050 | 1,050 |

โครงสร้าง view ต้องบังคับให้ถูกโดยอัตโนมัติ ไม่ใช่พึ่งความจำของคนเขียนโค้ด

### บั๊กที่ต้องแก้ไปพร้อมกัน — ประกันมือให้ "วันทำงานผี"

หน้ารายงานที่ deploy ไปแล้ว (`src/app/(app)/reports/page.tsx`) จัดกลุ่มด้วย
`${sale_date}|${therapist_id}` ซึ่งทำให้รายการขายที่**ไม่ได้ระบุหมอนวด**
กลายเป็นกลุ่มหนึ่งและได้ประกัน ฿500 ต่อวันไปด้วย

| เดือน | รายการไม่ระบุหมอ | วันที่ได้ประกันผี | ค่ามือปลอม |
| ----- | ---------------- | ----------------- | ---------- |
| เม.ย. 69 | 4 | 4 | 2,000 |
| มิ.ย. 69 | 2 | 2 | 1,000 |
| ก.ค. 69 | 1 | 1 | 500 |
| **รวม** | **7** | **7** | **3,500** |

เป็นบั๊กชนิดเดียวกับที่เคยเจอ — กฎประกันถูกใช้กับสิ่งที่ไม่ใช่ "หมอ 1 คนใน 1 วัน"

**การแก้:** `v_therapist_daily` ต้องมี `where therapist_id is not null`
พอทุกหน้าดึงจาก view เดียวกัน บั๊กนี้จะหายทั้งระบบโดยอัตโนมัติ
และเป็นเหตุผลสนับสนุนแนวทาง A โดยตรง

### `v_therapist_daily`

```
work_date · therapist_id · sessions · total_commission · request_fee
guarantee_amount · net_commission · total_income · status · is_paid
```

ตรรกะที่ฝังไว้ที่เดียว:

- `worked = sessions > 0`
- `net_commission = worked ? MAX(total_commission, ประกัน) : 0`
- ค่าประกันอ่านจาก `settings.min_commission_guarantee` ไม่ hardcode

หน้าค่ามือรายวัน หน้าสรุปข้ามวัน และรายงานรายเดือน ต้องดึงจาก view นี้ทั้งหมด

### `v_daily_summary`

```
sale_date · sessions · gross_sales · net_revenue · discount_total · cash_in
```

- `net_revenue` = ผลรวม `revenue_recognize`
- `cash_in` = ยอดขายที่ไม่ใช่ Member Credit + เงินเติมสมาชิกของวันนั้น

`cash_in` ใส่ตั้งแต่เฟส 1 เพราะต้นทุนแทบเป็นศูนย์ และกันการต้องแก้ view ในเฟส 2

### ความปลอดภัย

ทุก view ใช้ `security_invoker = true` — RLS ยังทำงานปกติ ไม่เป็นช่องหลบสิทธิ์

`v_monthly_pl` **ไม่ทำในเฟสนี้** เพราะต้องรอให้เจ้าของร้านตรวจการจัดประเภทต้นทุนก่อน
ถ้าทำตอนนี้จะได้ P&L ที่ตั้งอยู่บนการเดา

| หมอ | วัน | งาน | ค่ามือจริง | ใช้ประกัน | รวมจ่าย |
| --- | --- | --- | --- | --- | --- |
| แพท | 29 | 88 | 24,095 | 3 วัน | 24,725 |

| … | | | | | |
| รวม | | 527 | 134,715 | 32 วัน | 140,415 |

กดชื่อหมอเพื่อดูรายวันของคนนั้น

เลือกทำทั้งสองเพราะตอบคนละคำถาม ไม่ใช่เพราะอยากได้ครบ

## กรณีพิเศษ

- **ช่วงเวลาคร่อมเดือน** — ประกันคิดรายวันอยู่แล้ว ถูกโดยอัตโนมัติ
- **หมอลาออกกลางช่วง** — ยังต้องแสดงในช่วงที่เคยทำงาน
- **วันที่ไม่มียอดขาย** — แสดง 0 ไม่ข้ามไป ไม่งั้นค่าเฉลี่ยต่อวันสูงเกินจริง
- **ช่วงที่ไม่มีข้อมูลเลย** — แสดงข้อความ "ไม่มีข้อมูลในช่วงนี้"
  ไม่ใช่โชว์ 0 เฉยๆ ให้เข้าใจผิดว่าขายไม่ได้
- **เวลาไทยทุกจุด** — ตัวกรองวันที่ใช้ `Asia/Bangkok` เสมอ ผ่าน `src/lib/datetime.ts`
