# Spec: รับจองออนไลน์ผ่าน LINE OA (เฟส 1 ของงาน LINE)

> สถานะ: ผ่านการ brainstorm กับเจ้าของร้านครบทุกส่วนเมื่อ 2026-07-24
> เฟสถัดไป (คนละ spec): CRM สะสม point/แลกรางวัลในไลน์ — ใช้ "ตัวผูกตัวตน LINE↔ลูกค้า" จาก spec นี้เป็นฐาน

## เป้าหมาย

ลูกค้าจองคิวนวดเองจาก LINE OA ของร้าน → คำขอโผล่เป็นการ์ด "รออนุมัติ" บนบอร์ดคิววันนี้
→ พนักงานกดรับ/ปฏิเสธ → ระบบแจ้งผลกลับเข้าไลน์ลูกค้าอัตโนมัติ
ลดงานรับจองทางแชท/โทร และบังคับวางฐาน LINE Login ที่เฟส CRM ใช้ต่อ

## การตัดสินใจที่ปิดแล้ว (จากการ brainstorm)

| เรื่อง | ตัดสินใจ |
|---|---|
| ลำดับงาน | จองออนไลน์ก่อน · CRM point เฟสถัดไป |
| การยืนยันคิว | พนักงานกดยืนยันก่อนเสมอ (ไม่มี auto-confirm) |
| สิ่งที่ลูกค้าเลือก | เมนู + วัน + เวลา เป็นหลัก · หมอเลือกได้ถ้าอยาก = นับเป็นรีเควส +40฿ อัตโนมัติ · ไม่เลือก = ร้านจัดให้ |
| จองกลุ่ม | ระบุจำนวนคน 1–4 + เมนูรายคน → สร้างการ์ดคิวหลายใบผูก group_id เดิม |
| แจ้งเตือน | ① รับคำขอ ② ยืนยัน ③ ปฏิเสธ(พร้อมเหตุผล) ④ ยืนยันการยกเลิก — ผ่าน LINE push |
| การยกเลิกโดยลูกค้า | ได้จนถึงก่อนเวลานัด 2 ชั่วโมง |
| สถาปัตยกรรม | แนวทาง A: หน้า /book (LIFF) ในโปรเจกต์ POS เดิม + Messaging API |
| UI ฝั่งลูกค้า | แบบ Wizard ทีละขั้น (จำนวนคน → เมนูรายคน → วันเวลา → หมอ → สรุป/ยืนยัน) โทน CI ครีม/น้ำตาลแดง |
| เตือนก่อนถึงนัด 1 ชม. | ไม่ทำในเฟสนี้ (ต่อเติมทีหลังได้ ไม่กระทบโครง) |

## สถาปัตยกรรม

```
LINE OA (rich menu "จองคิว")
  → เปิด LIFF: หน้า /book ใน sookkaya-pos-v2 (public route, ธีม CI)
  → server action ตรวจ LIFF idToken กับ LINE → สร้างการ์ดคิว status='pending'
  → บอร์ด "คิววันนี้" (realtime เดิม) โชว์การ์ดรออนุมัติ
  → พนักงานกด รับ/ปฏิเสธ/แก้ไขก่อนรับ
  → LINE Messaging API push ข้อความแจ้งผลถึงลูกค้า
```

ไม่มีบริการ/repo ใหม่ — ทุกอย่างอยู่ใน Next.js + Supabase + Vercel (sin1) เดิม

### ชิ้นส่วนที่สร้างใหม่ 5 ชิ้น

1. **หน้า `/book` (LIFF, public)** — wizard 5 ขั้น: จำนวนคน → เมนูรายคน → วัน+เวลา → หมอ(ไม่บังคับ) → สรุป+เบอร์โทร+ส่งคำขอ · หน้า `/book/mine` "การจองของฉัน" (ดู+ยกเลิก)
2. **ตัวผูกตัวตน LINE↔ลูกค้า** — ตาราง `line_accounts` · ครั้งแรกขอเบอร์โทรหนึ่งครั้งเพื่อจับคู่/สร้างลูกค้า · ครั้งถัดไปจำได้เลย
3. **สถานะคิวใหม่** — `pending` (รออนุมัติ) และ `rejected` (ถูกปฏิเสธ ไม่แสดงบนบอร์ด) + ปุ่ม รับ / ปฏิเสธ(เลือกเหตุผล) / แก้ไขก่อนรับ ใน dialog การ์ด
4. **ตัวส่งข้อความไลน์** (`lib/line.ts` + credentials ใน env) — push 4 จังหวะ ผ่าน Messaging API
5. **การแจ้งพนักงาน** — ป้ายจำนวนคำขอค้างบนเมนู "คิววันนี้" + การ์ดเด้ง realtime + แถบสรุป "⏳ รออนุมัติ N" หัวบอร์ด

## Data model

### ตารางใหม่ `line_accounts`
```sql
create table line_accounts (
  line_user_id text primary key,      -- จาก LINE (ยืนยันผ่าน idToken แล้วเท่านั้น)
  customer_id  uuid references customers(id) not null,
  display_name text,
  picture_url  text,
  phone        text,                  -- เบอร์ที่กรอกตอนผูก (ไว้ให้พนักงานตรวจ)
  created_at   timestamptz default now()
);
```
- ผูกครั้งแรก: เบอร์ตรง customers.phone หนึ่งคน → ใช้คนนั้น · ตรงหลายคน → เลือกคนที่มีบิลล่าสุด · ไม่ตรง → สร้างลูกค้าใหม่ (name = ชื่อ LINE, phone = เบอร์ที่กรอก)
- RLS: ไม่เปิดให้ anon/authenticated อ่านตรง — เข้าถึงผ่าน server actions ที่ตรวจ idToken เท่านั้น

### ต่อยอด `queue_entries` (ตารางเดิม)
- ขยาย check ของ `status`: เพิ่ม `'pending'`, `'rejected'`
- คอลัมน์ใหม่: `line_user_id text` (การจองจากไลน์), `reject_reason text`
- คำขอจากไลน์: `source='booking'`, `booking_channel='line'` (ค่าเดิมที่มีอยู่แล้ว), `is_request` ตามเลือกหมอ, กลุ่มใช้ `group_id` เดิม
- การ์ด `pending`: **ไม่บล็อกช่องเวลา** (walk-in ทับได้ ร้านตัดสินเอง) · เลยเวลานัดแล้วยังไม่กดรับ → ขอบส้มเตือน
- กดรับ → `status='waiting'` (คิวปกติทุกประการ: เก็บเงิน/ลาก/กลุ่ม ใช้ของเดิม) · ปฏิเสธ → `'rejected'` + เหตุผล

### สิ่งที่ไม่แตะ
สูตรเงิน · sales · ค่ามือ · reconciliation — การจองเป็นผังงานล้วน เงินเกิดตอนเก็บเงินหน้าร้านเหมือนเดิม

## กติกาช่วงเวลาที่เปิดให้จอง

- ช่องละ 30 นาที ตั้งแต่ 10:00 ถึง 21:00 (คิวสุดท้ายต้องจบก่อนร้านปิด 22:00 ตามความยาวเมนู)
- จองได้ตั้งแต่ "ตอนนี้ + 1 ชม." จนถึงล่วงหน้า 14 วัน
- ระบบ**ไม่เช็คว่าหมอว่างจริง** (สอดคล้องกับ staff-approve) — โชว์เป็น "ช่วงเวลาที่ร้านเปิดรับ" และร้านเป็นผู้ยืนยัน

## ความปลอดภัย (3 ชั้น)

1. **ตรวจตั๋วกับ LINE เสมอ** — ทุก server action ของ /book รับ LIFF idToken แล้ว verify กับ LINE endpoint (ตรวจ channel id + หมดอายุ) ฝั่งเซิร์ฟเวอร์ ได้ line_user_id ที่เชื่อถือได้ · ไม่เชื่อค่าใดๆ ที่ client ส่งตรง
2. **เห็นเฉพาะของตัวเอง** — ทุก query ฝั่งลูกค้า filter ด้วย line_user_id ที่ verify แล้วเท่านั้น · การกรอกเบอร์คนอื่นตอนผูกบัญชี ไม่ทำให้เห็นข้อมูล/เครดิต/การจองของใคร
3. **ประตูแคบ** — ลูกค้าทำได้ 3 อย่าง: สร้างคำขอ / ดูของตัวเอง / ยกเลิก (เฉพาะ pending·waiting ของตัวเอง และเหลือ ≥2 ชม. ก่อนนัด) · จำกัด pending ค้างไม่เกิน 3 คำขอ · คำขอซ้ำภายใน 1 นาทีนับครั้งเดียว · server actions ใช้ client สิทธิ์จำกัดเฉพาะงานนี้ ไม่ reuse ของพนักงาน

## ข้อความไลน์ 4 จังหวะ (ตาม mockup ที่อนุมัติ)

1. **รับคำขอแล้ว** (ทันทีที่ส่ง): สรุปวัน เวลา เมนู จำนวนคน หมอ/รีเควส + "⏳ รอร้านยืนยัน"
2. **ยืนยันแล้ว**: สรุปนัด + ลิงก์ [ดู/ยกเลิกการจอง]
3. **ปฏิเสธ**: ขออภัย + เหตุผลที่พนักงานเลือก (คิวเต็ม/หมอไม่อยู่/อื่นๆ+พิมพ์เอง) + ลิงก์ [จองเวลาใหม่]
4. **ยกเลิกแล้ว** (ลูกค้ากดเอง): ยืนยันการยกเลิก + ลิงก์ [จองคิวใหม่]

## การรับมือเคสผิดพลาด

| เคส | พฤติกรรม |
|---|---|
| push ไลน์ไม่สำเร็จ (ลูกค้าบล็อก OA ฯลฯ) | การจองเดินหน้าปกติ · การ์ดติดหมายเหตุ "ส่งไลน์ไม่ผ่าน — โทรแจ้ง" |
| กดส่งซ้ำ (เน็ตช้า) | dedupe ฝั่งเซิร์ฟเวอร์ภายใน 1 นาที |
| pending ค้างเกิน 3 | หน้าจองแจ้ง "มีคิวรอยืนยันอยู่" ไม่รับเพิ่ม |
| เลยเวลานัดแต่ร้านยังไม่กด | การ์ดขอบส้มเตือน · ลูกค้ายังยกเลิกได้ |
| idToken หมดอายุ/ปลอม | หน้า /book แจ้งให้เปิดใหม่จากไลน์ ข้อความสุภาพ ไม่ leak รายละเอียด |

## แผนทดสอบ

- **TDD lib ล้วน**: `lib/booking-slots.ts` (คำนวณช่องเวลา: ขอบเปิด-ปิดร้าน, ตัดอดีต, เมนูยาวจบไม่ทัน), กติกายกเลิก 2 ชม., dedupe window — vitest ตามแบบแผนโปรเจกต์
- **ผูกตัวตน**: เบอร์ตรงหนึ่งคน / หลายคน (เลือกคนบิลล่าสุด) / ไม่ตรง (สร้างใหม่)
- **เส้นทางเต็มบน LINE จริง (มือ)**: จองเดี่ยว · กลุ่ม 3 คน เมนูต่างกัน · เลือกหมอ (ต้องเห็นรีเควส +40 ตอนเก็บเงิน) · รับ/ปฏิเสธ/แก้เวลาก่อนรับ · ลูกค้ายกเลิก — เช็ค push ครบ 4 จังหวะ
- **ความปลอดภัย**: ยิง action ด้วย idToken ปลอม/หมดอายุ/ไม่ส่ง → ถูกปฏิเสธทั้งหมด · พยายามยกเลิกคิวของ line_user_id อื่น → ถูกปฏิเสธ

## สิ่งที่ต้องเตรียมนอกโค้ด (เจ้าของร้านทำใน LINE Developers Console)

1. สร้าง Messaging API channel ผูกกับ LINE OA ของร้าน → ได้ `LINE_CHANNEL_ACCESS_TOKEN`
2. สร้าง LIFF app (ขนาด Full) ชี้ไปที่ `https://sookkaya-pos.vercel.app/book` → ได้ `LIFF_ID` และ `LINE_CHANNEL_ID` (ของ LIFF/Login channel)
3. ตั้ง rich menu ใน OA Manager: ปุ่ม "จองคิว" เปิดลิงก์ LIFF
4. ใส่ env ใน Vercel: `LINE_CHANNEL_ACCESS_TOKEN`, `LINE_LOGIN_CHANNEL_ID`, `NEXT_PUBLIC_LIFF_ID`

## นอกขอบเขตเฟสนี้ (จดไว้กันหลงประเด็น)

- CRM สะสม point / แลกรางวัล (เฟสถัดไป — ใช้ line_accounts ต่อ)
- เตือนก่อนถึงนัด 1 ชม. (ต้องมี cron — เพิ่มทีหลังได้)
- มัดจำ/จ่ายเงินออนไลน์
- Auto-confirm / ระบบวันหยุด-กะหมอ

## บทเรียนจากระบบจอง ThaiHand (วิเคราะห์จากวีดีโอ 24 ก.ค. 2026)

ดู flow จริงของ thaihandpos.com (wizard 3 ขั้น: วันเวลา → เลือกบริการ → ชำระเงิน) แล้วคัดมาปรับใช้:

**รับมาใช้ในเฟสนี้:**
1. **หมายเหตุ/ความต้องการพิเศษต่อการจอง** — ThaiHand ให้ใส่ "หมายเหตุส่วนตัว" รายคน · ของเราเพิ่ม 1 ช่อง (ทั้งกลุ่มใช้ร่วมกัน) ในขั้นสรุป → ลง `queue_entries.notes` ซึ่งการ์ดคิวฝั่งร้านแสดงอยู่แล้ว
2. **"ใช้เมนูเดียวกันทุกคน"** — ThaiHand มี checkbox กำหนดเมนูให้ลูกค้าทุกคน · ของเราเพิ่มปุ่มลัดในขั้นเลือกเมนู (คัดลอกเมนูคนที่ 1 ให้ทุกคน) ลดการกดตอนมาเป็นกลุ่ม
3. **ข้อความยืนยันบอกวิธีชำระ + เวลามาถึง** — ข้อความ LINE ของ ThaiHand ระบุ "ชำระเงินที่หน้าร้าน · โปรดมาถึงก่อนเวลานัดหมาย 15 นาที" ชัดมาก · เพิ่มสองบรรทัดนี้ใน msgConfirmed ของเรา
4. **จองซ้ำ + ประวัติการจอง** — ThaiHand มีปุ่ม "จองซ้ำ" บนทุกรายการในประวัติ · ของเราเพิ่มส่วน "การจองที่ผ่านมา" (5 รายการล่าสุด) ใน /book/mine พร้อมปุ่มจองซ้ำที่พาเข้า wizard โดยเติมเมนู/จำนวนคนเดิมให้ (เลือกวันเวลาใหม่)
5. **ยอมรับเงื่อนไขสุขภาพก่อนจอง** — ThaiHand มีหน้า consent อาการต้องห้ามนวด · ของเราใช้แบบเบา: บรรทัดเดียวในขั้นสรุป "การกดจอง = ยืนยันว่าไม่มีอาการต้องห้ามนวด (ดูรายการ)" กดดูเป็น dialog ไม่เพิ่มขั้นตอน

**ดูแล้วไม่รับ (พร้อมเหตุผล):**
- เลือกสาขา — ร้านเรามีสาขาเดียว
- เลือกเพศหมอ / หลีกเลี่ยงหมอ — หมอเรามีไม่กี่คน เลือกชื่อตรงๆ ครอบคลุมกว่า
- จ่ายด้วยแพ็กเกจ/เครดิตออนไลน์ — ของเราเก็บเงินที่ร้าน (เครดิตเมมเบอร์ไปเฟส CRM)
- Auto-confirm ทันที (ThaiHand ยืนยันเองเลย) — เราเลือก staff-approve แล้ว เหมาะกับร้านที่หมอ/เตียงจำกัด
- รูปภาพประกอบเมนู + ค้นหา/หมวดหมู่ — เมนูเรามี ~13 รายการ select ธรรมดาพอ (รูปไว้เฟสหน้า)
- เลขที่การจอง (#12345) — ร้านเล็ก ระบุชื่อ+เวลาโทรคุยได้
