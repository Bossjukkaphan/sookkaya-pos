# แบ่งชำระ: เครดิตสมาชิก + อีกหนึ่งช่องทาง ใน 1 บิล

วันที่: 2026-07-31 · สถานะ: เจ้าของร้านอนุมัติแนวทางแล้ว (ทางเลือก C จากการคุย)

## ปัญหา

ลูกค้าสมาชิกมาใช้บริการแต่เครดิตคงเหลือไม่พอทั้งบิล ต้องจ่ายส่วนต่างด้วยเงินโอน
ระบบบล็อกที่ `sale-actions.ts` ("เครดิตคงเหลือไม่พอ") — บันทึกบิลไม่ได้เลย ไม่มีทางออก

## ขอบเขต (ตัดสินใจแล้ว)

- **ทำ:** เครดิตสมาชิกบางส่วน + อีก **หนึ่ง** ช่องทาง (QR/เงินสด/บัตร) ใน 1 บิล
- **ไม่ทำรอบนี้:** เงินจริงสองก้อนในบิลเดียว (เช่น บัตร+โอน) — ยังไม่มีเคสจริง
  แก้ขัดด้วยการเปิดสองบิล · ถ้าอนาคตเจอบ่อยค่อยยกเป็นตารางรายการชำระ (design B)
  ซึ่งดีไซน์นี้ไม่ขวางทาง (migrate จาก `credit_used`+`payment_method` ได้เสมอ)
- **ค่าเริ่มต้น:** ใช้เครดิตที่เหลือให้หมดก่อน พนักงานแก้ตัวเลขลงได้
  (เช่น ลูกค้าขอเก็บเครดิตไว้) แก้ขึ้นเกินเครดิตที่เหลือไม่ได้

## หลักการ

ใช้โครงข้อมูลเดิม — `sales.credit_used` แยกจาก `payment_method` อยู่แล้ว:

- `payment_method` = ช่องทางของ**เงินจริง** (QR/เงินสด/บัตร) — หรือ "Member Credit"
  เมื่อเครดิตจ่ายทั้งบิล (พฤติกรรมเดิมไม่เปลี่ยน)
- `credit_used` = ยอดที่ตัดจากเครดิต (0 ถึง net_amount)
- **ไม่เพิ่มตาราง/คอลัมน์ใหม่** — บิลเก่าทุกใบตีความได้ด้วยกติกาเดียวกันโดยไม่ต้องแก้ข้อมูล

## 1. สูตรเงิน — `src/lib/sale-math.ts` (ที่เดียวที่แตะสูตร)

เพิ่ม input: `creditRequested: number` (0 = ไม่ใช้เครดิต)

```
creditUsed        = min(creditRequested, netAmount)
bonusUsed         = round2(creditUsed × (1 − ratio))     // ratio = cash_paid / credit_granted
revenueRecognize  = netAmount − bonusUsed
```

**พิสูจน์ว่าเข้ากันได้กับสูตรเดิม (ต้องมีเทสยืนยันทั้งสองเคส):**
- บิลเครดิตเต็ม: `creditUsed = netAmount` → `revenueRecognize = netAmount × ratio` = สูตรเดิมเป๊ะ
- บิลไม่ใช้เครดิต: `creditUsed = 0` → `revenueRecognize = netAmount` = สูตรเดิมเป๊ะ
- ผลคือ **ข้อมูลเก่าทุกแถวตัวเลขไม่ขยับ** — reconciliation 29 ข้อต้อง PASS เท่าเดิม

ตัวอย่าง: บิล 800 · เครดิตเหลือ 500 · โอน 300 · Silver (ratio 5000/6000)
→ creditUsed 500 · bonusUsed 83.33 · revenueRecognize 716.67 · เงินเข้าจริง 300

`payment_method` ของบิลแบ่งจ่าย = ช่องทางของเงินจริง (เช่น "QR Code") ไม่ใช่ "Member Credit"
— "Member Credit" ใช้เฉพาะเมื่อเครดิตจ่ายทั้งบิล (ตรงกับความหมายเดิมของข้อมูลเก่า)

## 2. การตรวจเครดิต — `sale-actions.ts`

- เดิม: จ่ายด้วยเครดิต → ต้องมีเครดิต ≥ ทั้งบิล ไม่งั้น error
- ใหม่: `creditRequested ≤ เครดิตคงเหลือ` และ `creditRequested ≤ netAmount` ไม่งั้น error
- `credit_after` (โชว์บนใบเสร็จ) = คงเหลือ − creditUsed เหมือนเดิม
- แก้บิลย้อนหลัง: ใช้กลไก headroom เดิม (คืนเครดิตของบิลเดิมก่อนคิดใหม่)

## 3. หน้าจอ POS — `pos-form.tsx`

- เลือกลูกค้าที่มีเครดิต > 0 → แสดงช่อง **"ใช้เครดิต"** เติมค่า = min(เครดิตคงเหลือ, ยอดบิล)
  ให้อัตโนมัติ พนักงานแก้ลงได้ (รวมแก้เป็น 0)
- บรรทัดสรุปสด: `เครดิต 500 · ต้องเก็บเพิ่ม 300 บาท` → ถ้าส่วนเพิ่ม > 0
  บังคับเลือกช่องทางเงินจริง (QR/เงินสด/บัตร)
- เครดิตพอทั้งบิล → เหมือนเดิมทุกอย่าง (เลือก "Member Credit" จบ)
- ลูกค้าไม่ใช่สมาชิก/เครดิตหมด → ไม่แสดงช่อง ไม่มีอะไรเปลี่ยน

## 4. แต้มสะสม — `earnsPoints` ใน `sale-actions.ts`

กฎเดิม "เครดิตไม่ได้แต้ม (ได้ไปแล้วตอนเติม)" ตีความให้ถูกตอนแบ่งจ่าย:
- แต้มคิดจาก **ส่วนที่จ่ายเงินจริงเท่านั้น**: `floor((net_amount − credit_used) / 100)`
- บิลเครดิตเต็ม → 0 แต้ม (เท่าเดิม) · บิล QR ล้วน → เท่าเดิม
- ช่องทางที่ได้แต้มยังจำกัด เงินสด/QR/บัตร เหมือนเดิม (Gowabi/KOL ไม่ได้)

## 5. รายงานยอดตามช่องทาง

ทุกจุดที่รวมยอดตาม `payment_method` (หน้า /today · /finance · export) เปลี่ยนเป็น:

```
ช่องทางที่ระบุในบิล += net_amount − credit_used
"Member Credit"    += credit_used
```

กติกานี้ถูกกับบิลเก่าทุกใบ: บิลปกติ credit_used=0 · บิลเครดิตเต็ม credit_used=net_amount
→ **ไม่ต้อง migrate ข้อมูล** · ยอดต่อช่องทาง = เงินที่เข้าช่องทางนั้นจริง

## 6. บิลชุด (หลายรายการ ลูกค้าเดียว จ่ายครั้งเดียว)

เครดิตที่ใช้เฉลี่ยลงแต่ละรายการ**ตามสัดส่วน net ของรายการ** เศษปัดลงรายการสุดท้าย
เพื่อให้ `sum(credit_used) = เครดิตที่ตัดจริง` เป๊ะ — ด่าน `bill_id_inconsistent_bills`
ยังตรวจ payment_method เดียวกันทั้งชุดได้เหมือนเดิม (ทั้งชุดใช้ช่องทางเงินจริงเดียวกัน)

## 7. ด่านตรวจใหม่ (เพิ่มใน `supabase/reconciliation.sql`)

- `credit_used_exceeds_net` = 0 — ห้ามตัดเครดิตเกินยอดบิล
- `credit_used_without_customer` = 0 — บิลที่ตัดเครดิตต้องผูกลูกค้าเสมอ
- ด่านเดิมทั้ง 29 ข้อต้อง PASS ค่าเดิม (โดยเฉพาะ net_revenue/profit ทุกเดือน —
  พิสูจน์ว่าสูตรใหม่ไม่กระทบเลขเก่า)

## การทดสอบ

1. **เทสเทียบสูตร**: สูตรใหม่ต้องให้ผลตรงสูตรเดิมทุกเคสขอบ (เครดิตเต็ม/ศูนย์/มี ratio/ไม่มี)
2. เทสแบ่งจ่าย: ตัวอย่างบิล 800 ข้างบน + เศษสตางค์ + creditRequested เกินเครดิต/เกินบิล
3. เทสแต้ม: แบ่งจ่ายได้แต้มจากส่วนเงินจริง
4. เทสเฉลี่ยบิลชุด: ผลรวมตรงเป๊ะ
5. รัน reconciliation บน production หลัง deploy — 31 ข้อ (29 เดิม + 2 ใหม่) PASS ครบ

## สิ่งที่ตั้งใจไม่ทำ

- เงินจริง ≥2 ช่องทางในบิลเดียว (design B — รอเคสจริง)
- ใช้เครดิตของลูกค้าคนอื่นจ่ายให้ (เคสเดียร์สอนไว้ว่าอย่าเปิดช่องนี้โดยไม่มีระบบยืนยัน)
- แตะสูตรค่ามือหมอ — คิดจากบริการ ไม่เกี่ยวกับวิธีจ่าย
