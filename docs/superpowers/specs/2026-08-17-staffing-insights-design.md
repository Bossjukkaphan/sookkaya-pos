# หน้า "จัดกำลังหมอ" — /insights/staffing

**วันที่:** 2026-08-17
**สถานะ:** อนุมัติแล้ว รอเขียนแผน

## ที่มา

Boss เพิ่มหมอเป็น 7 คนในเดือน ส.ค. 2569 แล้วถามว่า (1) คุ้มไหม ควรจัด 7 คนถาวรหรือเปล่า
(2) จะใช้อะไรตัดสินว่าถึงเวลาเพิ่มเป็น 8 การวิเคราะห์ตอบคำถามนี้ทำในแชทไปแล้ว
(17 ส.ค. 2569) ข้อสรุปคือ

- เสาร์-อาทิตย์มีหลักฐานหนักแน่นว่า 7 คนคุ้ม: ครึ่งหนึ่งของวันมีช่วงที่หมอทั้ง 7 ติดคิวพร้อมกัน
  และยอดต่อหมอไม่ตก (2,953฿ ที่ 7 คน เทียบ 2,755฿ ที่ 6 คน)
- วันจันทร์-พฤหัสตรงข้าม: 5 คนได้ยอดต่อหมอ 2,248฿ สูงกว่า 6 คนที่ได้ 1,780฿
  งานวันธรรมดารองรับ ~5 คน
- ศุกร์พฤติกรรมใกล้เสาร์-อาทิตย์ (15,387฿) มากกว่าจันทร์-พฤหัส (11,033฿)
- การเพิ่มเป็น 8 ยังตัดสินไม่ได้ เพราะข้อมูลลูกค้าที่ปฏิเสธ (`turn_aways`) มีแค่ 5 แถว
  ทั้งระบบ — พนักงานยังไม่กดปุ่มปฏิเสธเป็นนิสัย

Boss ต้องการให้การวิเคราะห์นี้อยู่บนหน้าระบบถาวร ไม่ต้องมาถามใหม่ทุกเดือน

## สองคำถามที่หน้านี้ตอบ (Boss เลือก: ทั้งสอง แยกสองส่วนในหน้าเดียว)

1. **สัปดาห์นี้จัดกี่คนดี** — ดูตอนจัดตารางหมอ (คู่กับหน้า /shifts)
2. **ถึงเวลาจ้างคนที่ 8 หรือยัง** — ดูเดือนละครั้ง เกณฑ์ 4 ข้อ

## เส้นแบ่งข้อมูลที่ต้องเคารพ (Boss เลือกทาง ข.)

`attendance` ช่วง 8 มี.ค. – 26 ก.ค. 2569 (765 แถว) เป็นข้อมูล**เติมย้อนหลังจากบิล**
(`created_by = 'ประมาณจากบิลย้อนหลัง'`) ไม่ใช่การเช็คอินจริง — หมอที่มาแต่ไม่มีบิล
ไม่มีแถวในช่วงนี้ ตัวเลข "หมอว่างทั้งวัน" ของช่วงนี้จึงเป็น 0 เทียมโดยโครงสร้าง
การเช็คอินจริงเริ่ม **27 ก.ค. 2569**

การจัดการ: **แสดงข้อมูลทั้งหมด** เพื่อให้เห็นแนวโน้มข้ามเดือน แต่

- view มีคอลัมน์ `is_estimated` ต่อวัน
- หน้าแสดงป้ายเหลือง (แบบแผนเดียวกับ /insights/heatmap ที่บอกสัดส่วนรายการมีเวลา):
  *"การเช็คอินจริงเริ่ม 27 ก.ค. 2569 — ก่อนหน้านั้นประมาณจากบิล
  ตัวเลขที่พึ่งการเช็คอินตรง ๆ คำนวณจากช่วงข้อมูลจริงเท่านั้น"*
- ตัวชี้วัดที่พึ่งเช็คอินโดยตรง (เช่น หมอมาแล้วไม่ได้คิว) ใช้เฉพาะแถว `is_estimated = false`

## ขอบเขต

**ทำ**

1. view `v_staffing_daily` + `v_staffing_monthly` (ทั้งคู่ `security_invoker = true`)
2. pure functions ใน `src/lib/staffing.ts`: จำแนกประเภทวัน · จำนวนหมอแนะนำ ·
   สถานะเกณฑ์ 4 ข้อ
3. หน้า `/insights/staffing` สองส่วน + ป้ายความครบของข้อมูล
4. ลิงก์เมนูหมวดผู้บริหาร ชื่อ "จัดกำลังหมอ" (`minRole: "manager"`)

**ไม่ทำ**

- ไม่เพิ่มตารางวันหยุดนักขัตฤกษ์ — ใช้หมายเหตุ "วันหยุดนักขัตฤกษ์จัดตามการ์ดเสาร์-อาทิตย์"
  แทน (YAGNI — Boss รู้ปฏิทินวันหยุดเองอยู่แล้ว)
- ไม่ทำแจ้งเตือน/cron เมื่อเกณฑ์ผ่านครบ — หน้านี้ดูเดือนละครั้งตามจังหวะการตัดสินใจ
- ไม่แตะปุ่มปฏิเสธลูกค้าบนกระดานคิว — มีอยู่แล้ว ปัญหาคือวินัยการกด ไม่ใช่ระบบ
- ไม่แตะตาราง/ตัวเลขเงินใด ๆ — หน้านี้อ่านอย่างเดียว

## Global Constraints

- aggregate ทุกตัวมาจาก SQL view — ห้ามรวมเลขฝั่งหน้าเว็บ (1,000-row cap)
- ทุก view ต้องประกาศ `security_invoker = true` ในทุก `create or replace`
- วันที่ใช้ `(now() at time zone 'Asia/Bangkok')::date` — ห้าม `current_date`
- เวลาเริ่มครองคิวใช้ตรรกะเดียวกับ `bedStartMin()`: `started_at` ถ้ามี ไม่งั้น `start_time`
- migration ผ่าน MCP `apply_migration` (project `jrioyrmicioqammeevgh`) แล้วเก็บสำเนาลง
  `supabase/migrations/` เสมอ
- คอมเมนต์และข้อความหน้าจอเป็นภาษาไทย · ชื่อตัวแปรภาษาอังกฤษ
- ฟีเจอร์นี้ไม่แตะเงิน — หลังเสร็จรัน `supabase/reconciliation.sql` ต้องผ่าน 38/38
  ด้วย known exception ถาวรสองตัว: `bed_double_booked` = 1 (คู่ 9 ส.ค. 2569 เกิดก่อนคอลัมน์
  `bed_id_2` มีอยู่จริง) และ `therapist_double_booked` = 1 (คู่ 26 ก.ค. 2569 หมอโมเมกดปุ่มเริ่ม
  ผิดใบ) — ค่าเกิน 1 ของข้อไหนก็ตามคือมีคู่ใหม่ต้องสืบ ไม่ใช่ 0 ทั้งคู่ และยอด `v_daily_summary`
  ต้องไม่ขยับ
- ขึ้น production: push main แล้ว `vercel deploy --prod` เอง + เช็ค alias

## ส่วนที่ 1 — ข้อมูล

### `v_staffing_daily` — หนึ่งแถวต่อวันที่มีข้อมูล

| คอลัมน์ | นิยาม |
|---|---|
| `work_date` | วัน |
| `day_class` | `'mon_thu'` (isodow 1-4) · `'fri'` (5) · `'weekend'` (6-7) |
| `therapists_checked_in` | นับแถว `attendance` ที่ `therapist_id is not null` ของวันนั้น |
| `is_estimated` | `bool_or(created_by = 'ประมาณจากบิลย้อนหลัง')` ของวันนั้น |
| `bills` | นับแถว `sales` ที่ `therapist_id is not null` |
| `revenue` | `sum(net_amount)` ของแถวเดียวกัน |
| `revenue_per_therapist` | `revenue / nullif(therapists_checked_in, 0)` |
| `guarantee_shortfall_count` | จำนวนหมอในวันที่ค่ามือรวม < 500 — นับจากแหล่งเดียวกับ `v_therapist_daily` |
| `idle_therapists` | หมอที่เช็คอินแต่ไม่มีบิลในวัน — มีความหมายเฉพาะ `is_estimated = false` |
| `turn_away_count` | นับแถว `turn_aways` ของวัน |
| `peak_concurrent_therapists` | ค่าสูงสุดในวันของ "จำนวนหมอไม่ซ้ำที่ติดคิวพร้อมกัน" จาก `queue_entries` (status ไม่ใช่ cancelled/rejected, มี therapist_id) — จุดวัดคือเวลาเริ่มของแต่ละคิว ช่วงครองคือ `[start, start + duration_min)` โดย start = `started_at` (แปลงเขตเวลาไทย) ถ้ามี ไม่งั้น `start_time` |

### `v_staffing_monthly` — สรุปรายเดือนของเกณฑ์ 4 ข้อ

| คอลัมน์ | นิยาม |
|---|---|
| `month` | `YYYY-MM` |
| `weekend_days`, `weekend_full_days` | วันเสาร์-อาทิตย์ทั้งหมด และวันที่ `peak_concurrent_therapists >= therapists_checked_in` |
| `fri_sun_revenue_per_therapist` | เฉลี่ย `revenue_per_therapist` ของวันศุกร์-อาทิตย์ |
| `turn_away_total` | รวมทั้งเดือน |
| `guarantee_shortfall_pct` | `shortfall รวม / (หมอ-วัน รวม)` |
| `therapist_days`, `estimated_days` | ฐานนับ + จำนวนวันที่เป็นข้อมูลประมาณ |

## ส่วนที่ 2 — pure functions ใน `src/lib/staffing.ts`

```
dayClass(isoDate) → 'mon_thu' | 'fri' | 'weekend'

recommendedTherapists(rows) → { count, avgRevenue, avgPerTherapist, fullDayPct }
  rows = แถว v_staffing_daily ของ day_class เดียวกัน ช่วง 8 สัปดาห์ล่าสุด
  count = จำนวนหมอน้อยที่สุด n ที่ผ่านทั้งสองข้อ:
    (ก) ยอดต่อหมอเฉลี่ยของวันที่มีหมอ n คน ≥ 2,000฿
    (ข) สัดส่วนวันที่หมอยุ่งเต็มพร้อมกัน (peak >= n) ≤ 30%
  ถ้าไม่มี n ไหนผ่าน → คืน n ที่ยอดต่อหมอสูงสุด พร้อม flag inconclusive
  ถ้าข้อมูลของ n มีน้อยกว่า 3 วัน → ข้าม n นั้น (กันตัดสินจากวันเดียว)

criterionStatus(value, threshold, direction) → 'pass' | 'near' | 'fail'
  near = ยังไม่ผ่านแต่อยู่ภายใน 15% ของเกณฑ์

hireVerdict(months) → { passCount, verdict }
  verdict = 'ready' เมื่อเดือนปัจจุบันและเดือนก่อนหน้าผ่านครบ 4 ข้อติดกัน
```

เกณฑ์ 4 ข้อ (ค่าคงที่ตั้งต้น, export จาก `staffing.ts` ที่เดียว):

| # | เกณฑ์ | ผ่านเมื่อ |
|---|---|---|
| 1 | วันเสาร์-อาทิตย์ที่หมอยุ่งเต็มพร้อมกัน | ≥ 70% ของวัน |
| 2 | ยอดต่อหมอต่อวัน (ศุกร์-อาทิตย์) | ≥ 2,500฿ |
| 3 | ลูกค้าที่ปฏิเสธ | ≥ 8 ครั้ง/เดือน |
| 4 | หมอ-วันที่ต่ำกว่าการันตี 500฿ | ≤ 15% |

## ส่วนที่ 3 — หน้าจอ `/insights/staffing`

สิทธิ์: `canSeeInsights` (แบบแผนเดียวกับ insights อื่น — ไม่ผ่านแสดง `InsightsAccessDenied`)

**ป้ายความครบของข้อมูล** (การ์ดเหลือง บนสุด): ข้อความตามหัวข้อ "เส้นแบ่งข้อมูล" ข้างบน

**ส่วนบน "สัปดาห์นี้จัดกี่คนดี"** — การ์ด 3 ใบ (จันทร์-พฤหัส / ศุกร์ / เสาร์-อาทิตย์):

- ตัวเลขแนะนำตัวใหญ่ เช่น "5 คน" (ถ้า inconclusive แสดง "ข้อมูลยังไม่พอ" แทนตัวเลข)
- ใต้ตัวเลข: ยอดเฉลี่ย/วัน · ยอดต่อหมอ · % วันที่หมอเต็ม (จาก 8 สัปดาห์ล่าสุด)
- บรรทัดสุดท้ายของการ์ด: "หมอว่างทั้งวัน N ครั้ง" จาก `idle_therapists` รวมของ
  day_class นั้น **นับเฉพาะแถว `is_estimated = false`** — ตัวเลขนี้คือสัญญาณจ้างเกิน
  คู่ตรงข้ามกับ % วันที่หมอเต็มซึ่งเป็นสัญญาณจ้างขาด
- ใต้การ์ดเสาร์-อาทิตย์: "วันหยุดนักขัตฤกษ์จัดตามการ์ดนี้"

**ส่วนล่าง "ถึงเวลาจ้างคนที่ 8 หรือยัง"** — การ์ดเดียว:

- หัว: "ผ่าน X จาก 4 เกณฑ์ — ยังไม่ถึงเวลา / ถึงเวลาพิจารณา" (ready = 2 เดือนติดผ่านครบ)
- ตาราง 4 แถว: ชื่อเกณฑ์ · ค่าเดือนนี้ · เกณฑ์ · 🟢/🟡/🔴 · sparkline 6 เดือน
  (sparkline เป็น SVG เล็กในเซลล์ ไม่ใช้ไลบรารีกราฟเพิ่ม)
- ใต้แถวเกณฑ์ข้อ 3: ถ้าเดือนนี้ `turn_away_total < 4` แสดง
  *"ตัวเลขนี้เชื่อได้ต่อเมื่อพนักงานกดปุ่มปฏิเสธทุกครั้งที่รับลูกค้าไม่ได้ —
  เดือนนี้บันทึกเพียง N ครั้ง"* (ป้ายนี้แสดงตามจำนวนบันทึก ไม่เกี่ยวกับผ่าน/ไม่ผ่าน)

**เมนู** — เพิ่มใน `src/lib/nav.ts` หมวดผู้บริหาร:

## ส่วนที่ 4 — การทดสอบ

- `dayClass`: ครบ 7 วัน + ขอบเขต isodow
- `recommendedTherapists`: เคสปกติ · ไม่มี n ผ่าน (inconclusive) · n มีข้อมูล < 3 วัน ·
  ข้อมูลว่าง
- `criterionStatus`: pass / near (ขอบ 15% พอดี) / fail ทั้งสองทิศ (≥ และ ≤)
- `hireVerdict`: ผ่านเดือนเดียว → ไม่ ready · สองเดือนติด → ready · เดือนคั่น → ไม่ ready
- view: ยิง SQL ตรวจกับวันจริงที่รู้คำตอบ (เช่น 16 ส.ค. หมอเช็คอิน 7 · peak 7) —
  บันทึกเป็น query ตรวจรับในแผน ไม่เพิ่มเข้า reconciliation.sql เพราะไม่ใช่เรื่องเงิน
- ตรวจรับสุดท้าย: `reconciliation.sql` 38/38 PASS + ยอด 1-16 ส.ค. ใน `v_daily_summary`
  ไม่ขยับ

## หมายเหตุการตีความ

- "หมอยุ่งเต็มพร้อมกัน" เทียบ peak กับ**จำนวนที่เช็คอินวันนั้น** ไม่ใช่ค่าคงที่ 7 —
  วันที่จัด 5 คนแล้วเต็มทั้ง 5 ก็นับว่าเต็ม เพราะสัญญาณคือ "วันนั้นรับเพิ่มไม่ได้แล้ว"
- เกณฑ์ตัวเลข (2,000 / 2,500 / 70% / 30% / 8 ครั้ง / 15%) มาจากการวิเคราะห์ 17 ส.ค. 2569
  เก็บเป็นค่าคงที่ใน `staffing.ts` ที่เดียว — อนาคตถ้าร้านโตจนเกณฑ์เก่าไม่เหมาะ แก้ที่เดียวจบ
