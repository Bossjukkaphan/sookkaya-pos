# ยืนยันการจ่ายค่ามือหมอและเงินเดือนพนักงาน — Design

**วันที่:** 3/8/2569
**สถานะ:** อนุมัติแล้ว (เจ้าของร้าน 3/8/2569)

## เป้าหมาย

ทุกงวดจ่ายเงิน (ค่ามือหมอ 3 งวด + เงินเดือนพนักงาน 1 งวดต่อเดือน) ต้องถูกติ๊กยืนยันว่า
"จ่ายแล้ว และตัวเลขถูกต้อง" เป็นสองขั้น: คนจ่ายติ๊ก → เจ้าของร้านรับรอง
พร้อมแช่แข็งตัวเลข ณ วันติ๊กไว้เป็นหลักฐานตรวจย้อนหลัง

## ที่มา

- 3/8/2569 เจอค่ามือหมอเดือน ก.ค. ถูกคีย์ซ้ำ 92,025 บาท และส่วนต่างจ่ายจริงกับระบบคำนวณ
  180 บาทที่**สืบไม่ได้** เพราะไม่มีบันทึกว่าตอนจ่ายเงินตัวเลขคือเท่าไหร่
- หมวดค่ามือหมอกับเงินเดือนพนักงานสลับกันมาแล้วทั้งเดือน มิ.ย. และ ก.ค.
- ปุ่ม "จ่ายแล้ว" รายวันรายหมอที่มีอยู่บนหน้าค่ามือไม่เคยถูกใช้เลย (ตาราง 0 แถว)
  เพราะร้านจ่ายเป็นงวด ไม่ได้จ่ายรายวัน — ฟีเจอร์นี้จึงทำงานระดับงวด

## ขอบเขต

**ทำ**
- กล่อง "ยืนยันการจ่าย" บนหน้า `/commission` (เห็นเฉพาะผู้จัดการ/เจ้าของร้าน)
- ตารางบันทึกการยืนยัน + ช่องเงินเดือนตั้งต้นในหน้าทีมงาน
- ด่านตรวจในชุด reconciliation กันแก้รายจ่ายเงียบๆ หลังปิดงวด

**ไม่ทำ (ตัดสินใจแล้ว)**
- สูตรคอมมิชชัน/เงินพิเศษของพนักงานประจำ — เงื่อนไขยังไม่ชัด เดือนไหนจ่ายเกินเงินเดือนตั้งต้น
  ให้เขียนเหตุผลตอนติ๊กแทน (เช่น "โบนัส +2,000") พอเงื่อนไขชัดค่อยกลับมาทำ
- ไม่แตะปุ่ม "จ่ายแล้ว" รายวันเดิม (ปล่อยไว้ ไม่ใช้ก็ไม่เกะกะ)
- ไม่มีแจ้งเตือนไลน์เมื่อค้างยืนยัน — ไว้ค่อยพิจารณา

## กติกา

**เดือนหนึ่งมี 4 งวดเสมอ**

| งวด | kind · period_no | ช่วงวันที่ |
|---|---|---|
| ค่ามือ 1-10 | commission · 1 | วันที่ 1–10 |
| ค่ามือ 11-20 | commission · 2 | วันที่ 11–20 |
| ค่ามือ 21-สิ้นเดือน | commission · 3 | วันที่ 21–สิ้นเดือน |
| เงินเดือนพนักงาน | salary · 0 | ทั้งเดือน |

**ตัวเลขสองฝั่งที่เทียบกัน**

| งวด | ระบบคำนวณ (computed) | จ่ายจริง (recorded) |
|---|---|---|
| ค่ามือ | `sum(v_therapist_daily.total_income)` ในช่วงงวด | รายจ่ายหมวด `HR / payroll (ค่ามือหมอ)` **จับคู่งวดตามชื่อรายการก่อน วันที่เป็นตัวสำรอง** (ดูล่าง) |
| เงินเดือน | `sum(staff_members.base_salary)` เฉพาะ `is_active` | รายจ่ายหมวด `เงินเดือนพนักงานประจำ` ในหน้าต่างเดือน + ผ่อนผัน 3 วัน |

**ทำไมฝั่ง recorded ไม่กรองตามวันที่ตรงๆ** — ตอนแรกสเปกนี้เขียนว่ากรองตาม `expense_date`
ในช่วงงวด และอ้างว่าพิสูจน์กับ ก.ค. แล้ว **ซึ่งเป็นการพิสูจน์ที่ผิด**: ตอนตรวจมือเราจับคู่ตาม
ชื่อรายการโดยไม่รู้ตัว ของจริงร้านคีย์งวด 11-20 ลงวันที่ 21/7 ถ้ากรองตามวันที่ งวด 11-20
จะเหลือแค่เงินเบิก 2,500 และงวด 21-31 จะนับ 46,645 ซ้ำ (subagent จับได้ตอนรัน SQL จริง 3/8/2569)

กติกาที่ถูกต้องตามพฤติกรรมร้าน — หน้าต่างรายจ่ายของเดือน = วันแรกของเดือนถึงวันที่ 3
ของเดือนถัดไป (ตรงกับ accounting window) แล้วจัดเข้างวดตามลำดับ:
1. ชื่อมีเครื่องหมายเดือนอื่น (`/N/` ที่ N ไม่ใช่เดือนนี้) → ไม่นับ
2. ชื่อบอกช่วงงวด ("11-20" เช็คก่อน "1-10" ก่อน "21-") + เครื่องหมายเดือนนี้ → เข้างวดตามชื่อ ไม่สนวันที่
3. ที่เหลือ (เงินเบิกล่วงหน้า ฯลฯ) → เข้างวดตาม `expense_date` · อยู่โซนผ่อนผันโดยชื่อไม่บอกงวด → ไม่นับ

ตรวจกับ ก.ค. จริง: งวด 1-10 → 47,880 (ต่าง +50) · งวด 11-20 → 49,145 (**ตรงเป๊ะ**) · งวด 21-31 → 54,195 (ต่าง +130)

**สองขั้น**
1. **ติ๊ก "จ่ายแล้ว"** — ผู้จัดการหรือเจ้าของร้าน · ระบบแช่แข็ง computed + recorded ณ วินาทีติ๊ก
   พร้อมชื่อคนติ๊กและเวลา · ถ้าสองฝั่งไม่เท่ากัน **ต้องกรอกเหตุผลก่อน** ถึงติ๊กได้
2. **รับรอง** — เจ้าของร้าน (admin) เท่านั้น · รับรองแล้วปิดงวด แก้ไม่ได้อีก
   ก่อนรับรอง คนติ๊กยกเลิกเพื่อติ๊กใหม่ได้ (เช่นเพิ่งคีย์รายจ่ายเพิ่ม)

**พนักงานลาออก** — ปิด `is_active` ในหน้าทีมงาน (มีอยู่แล้ว) → หลุดจากยอดคาดหวังเดือนถัดไปเอง
งวดที่รับรองไปแล้วไม่กระทบเพราะตัวเลขถูกแช่แข็งแล้ว

## สถาปัตยกรรม

### Migration

```sql
-- บันทึกการยืนยันการจ่ายรายงวด — แถวหนึ่งคือหนึ่งงวดของเดือน
create table public.payout_confirmations (
  id               uuid primary key default gen_random_uuid(),
  month            text not null,        -- '2026-08'
  kind             text not null check (kind in ('commission', 'salary')),
  period_no        smallint not null default 0,  -- 1|2|3 = งวดค่ามือ · 0 = เงินเดือน
  computed_amount  numeric not null,     -- แช่แข็ง ณ ตอนติ๊ก
  recorded_amount  numeric not null,     -- แช่แข็ง ณ ตอนติ๊ก
  variance_reason  text,                 -- บังคับเมื่อสองยอดไม่เท่ากัน
  paid_by          text not null,        -- ชื่อจาก profiles.full_name (convention เดียวกับ sales.created_by)
  paid_at          timestamptz not null default now(),
  endorsed_by      text,
  endorsed_at      timestamptz,
  unique (month, kind, period_no)
);
-- RLS: admin/manager เท่านั้น (ทั้งอ่านและเขียน) · การจำกัด "รับรองเฉพาะ admin"
-- บังคับใน server action เพราะ RLS แยกชนิดการ update ไม่ได้
```

`staff_members` เพิ่ม `base_salary numeric not null default 0`

### `src/lib/payout-periods.ts` (ใหม่ · TDD)

ที่เดียวของความจริงเรื่องงวด — pure function ไม่แตะฐานข้อมูล

```ts
export type PayoutPeriod = {
  kind: "commission" | "salary"
  periodNo: number          // 1|2|3 ค่ามือ · 0 เงินเดือน
  label: string             // "ค่ามือ 1-10" ฯลฯ
  from: string              // ISO วันแรกของช่วง
  to: string                // ISO วันสุดท้ายของช่วง
}

/** งวดทั้ง 4 ของเดือน — สิ้นเดือนคิดถูกทั้ง 28/29/30/31 */
export function payoutPeriodsOf(month: string): PayoutPeriod[]

/** ต้องกรอกเหตุผลไหม — ยอดไม่เท่ากันแม้แต่สตางค์เดียวคือต้อง */
export function needsReason(computed: number, recorded: number): boolean

export type ConfirmationStatus = "pending" | "paid" | "endorsed"
/** สถานะของงวดจากแถว confirmation (หรือ null ถ้ายังไม่ติ๊ก) */
export function statusOf(row: { endorsed_at: string | null } | null): ConfirmationStatus
```

### Server actions `src/app/(app)/commission/payout-actions.ts` (ใหม่)

- `markPayoutPaid(month, kind, periodNo, reason?)` — คำนวณสองยอดสดใน action (ไม่เชื่อ client)
  · ถ้าไม่เท่ากันและไม่มี reason → คืน error พร้อมยอดทั้งสอง ให้ฟอร์มโชว์ช่องเหตุผล
  · insert แถวแช่แข็ง
- `cancelPayoutPaid(id)` — ลบแถว เฉพาะที่ยังไม่ถูกรับรอง
- `endorsePayout(id)` — เช็ค role ต้องเป็น admin · เขียน endorsed_by/endorsed_at
- ทุก action ตรวจ error จริง ไม่รายงานสำเร็จทั้งที่ RLS กรองเงียบ (แบบเดียวกับ expense-actions)

### UI บนหน้า `/commission`

กล่อง "ยืนยันการจ่าย" อยู่บนสุดของหน้า **เฉพาะ role admin/manager** (ดึง `getMyProfile()`
— หน้าเดิมไม่เคยเช็ค role จึงต้องเพิ่ม แต่เนื้อหาเดิมของหน้ายังเปิดให้ทุกคนเหมือนเดิม)

- หน้าค่ามือเป็นมุมมองรายวัน (`?date=`) → กล่องแสดงงวดของ**เดือนที่วันนั้นอยู่** เปลี่ยนวันข้ามเดือนกล่องตามไปเอง
- 4 แถว แต่ละแถว: ชื่องวด · ยอดระบบคำนวณ · ยอดจ่ายจริง · ส่วนต่าง · สถานะ
- สถานะ 3 ระดับ: `รอจ่าย` (เทา) → `จ่ายแล้ว รอรับรอง` (เหลือง อยู่ในสายตาเจ้าของ) → `รับรองแล้ว ✓` (เขียว พร้อมชื่อ+วันที่ทั้งสองขั้น)
- แถวที่ยอดไม่ตรง โชว์เหตุผลที่กรอกไว้ใต้แถวเสมอ ไม่ต้องกดดู
- **ติ๊กได้ตั้งแต่วันสุดท้ายของงวดเป็นต้นไป** (งวด 1-10 ติ๊กได้ตั้งแต่วันที่ 10 · เงินเดือนตั้งแต่วันสิ้นเดือน)
  ก่อนหน้านั้นขึ้นจางไว้ และ `markPayoutPaid` ปฏิเสธฝั่ง server ด้วย ไม่ใช่แค่ซ่อนปุ่ม

## ความเสี่ยงที่รู้ตัว

- **เดือนเก่าก่อนมีระบบ (มี.ค.–ก.ค.) จะขึ้น "รอจ่าย" ทั้งที่จ่ายไปแล้ว** — ยอมรับ ไม่บังคับ
  ย้อนติ๊ก ถ้าเจ้าของอยากปิดย้อนหลังก็ติ๊กได้ตามปกติ (ตัวเลขคำนวณย้อนหลังได้อยู่แล้ว)
- **เงินเบิกล่วงหน้าที่เบิกงวดหนึ่งแต่หักอีกงวด** จะทำให้สองงวดต่างกันคนละทิศ (เช่น ก.ค.
  งวด 1-10 ต่าง +50) — เป็นธรรมชาติของการจ่ายเงินสด กรอบเหตุผลรองรับอยู่แล้ว
- **ถ้าอนาคตร้านเปลี่ยนรอบจ่าย** (เช่นเหลือ 2 งวด) แก้ที่ `payoutPeriodsOf` ที่เดียว
