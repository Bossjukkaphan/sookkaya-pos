# SOOKKAYA POS — บอร์ดคิวหมอนวด "คิววันนี้" (ลากจัดคิวได้)

วันที่: 2026-07-22
สถานะ: รออนุมัติ
แนวทางที่เคาะ: A — บอร์ดลากได้เต็มรูปแบบ (ผู้ใช้เลือกจาก A/B/C)

## ที่มา

เจ้าของร้านอยากได้บอร์ดจัดคิวแบบแอปจองคิว (ตามภาพตัวอย่างที่แนบ):
timeline รายหมอ × เวลา มีการ์ดบริการที่ลากย้ายหมอ/เลื่อนเวลาได้
เส้นเวลาปัจจุบัน สถานะกำลังนวด/ชำระแล้ว และสรุปหมอว่าง

ปัจจุบันระบบบันทึกการขายตอนเก็บเงินครั้งเดียว (sale_time = เวลากดบันทึก)
ไม่มีข้อมูลคิวก่อนเก็บเงิน — จึงต้องมีตารางคิวแยกต่างหาก

## การตัดสินใจที่เคาะแล้ว (จากการถามผู้ใช้)

| เรื่อง | เลือก |
| ------ | ----- |
| บทบาทบอร์ด | **คิวสดวันนี้** — การ์ดคิวเกิดก่อนเก็บเงิน ไม่ใช่มุมมองรายการขายย้อนหลัง และไม่ใช่ระบบจองข้ามวัน |
| ตำแหน่ง | **หน้าใหม่ `/queue` "คิววันนี้"** ในเมนูซ้าย ไม่ฝังในหน้า POS |
| เชื่อม POS | ปุ่ม "เก็บเงิน" บนการ์ด → เปิด `/pos?queue={id}` พร้อมหมอ+เมนู+ลูกค้ากรอกไว้แล้ว |
| เทคนิคลาก | เขียนเองด้วย pointer events (ไม่ใช้ dnd-kit) — แบบเดียวกับ tooltip กราฟที่พิสูจน์แล้วว่าเวิร์กบนแท็บเล็ต |

## หลักการเงิน (ห้ามละเมิด)

**คิวเป็นแค่ผังงาน ไม่ใช่เงิน** — ตาราง `queue_entries` ไม่มีคอลัมน์เงินสักช่อง
รายได้/ค่ามือ/เครดิต เกิดตอนบันทึกขายผ่าน `createSale` เท่านั้น (สูตรเดิมทุกอย่าง)
ผูกกันแค่ `queue_entries.sale_id` ชี้ไปใบขายหลังเก็บเงินแล้ว
→ reconciliation 21 ข้อไม่กระทบเลย

## ฐานข้อมูล

### ตารางใหม่ `queue_entries`

```sql
create table public.queue_entries (
  id            uuid primary key default gen_random_uuid(),
  queue_date    date not null,                 -- วันของคิว (เวลาไทย)
  therapist_id  uuid references therapists(id), -- null = ยังไม่ระบุหมอ (แถวพักคิว)
  service_id    uuid references services(id),
  service_name  text not null,                 -- snapshot กันเมนูถูกแก้/ปิดใช้
  duration_min  int  not null,                 -- ระยะเวลาของคิวนี้ (แก้รายคิวได้)
  customer_id   uuid references customers(id), -- ไม่บังคับ
  customer_name text,                          -- ไม่บังคับ (ลูกค้าใหม่ยังไม่มี id)
  start_time    time not null,
  status        text not null default 'waiting'
                check (status in ('waiting','in_service','paid','cancelled')),
  sale_id       uuid references sales(id),     -- ผูกเมื่อเก็บเงินแล้ว
  created_at    timestamptz not null default now(),
  updated_at    timestamptz not null default now()
);
```

- RLS: ทุก role ที่ล็อกอิน (staff/manager/admin) อ่าน-เขียนได้ — พนักงานคือคนจัดคิว
- index: `(queue_date)` — หน้าบอร์ดดึงเฉพาะวันนี้เสมอ
- สถานะ: `waiting` รอ · `in_service` กำลังนวด · `paid` ชำระแล้ว · `cancelled` ยกเลิก

### เพิ่ม `services.duration_min int`

- migration เติมค่าจากชื่อเมนู: regex `(\d+)\s*นาที` → เช่น "นวดไทย 60 นาที" = 60
- เมนูที่ชื่อไม่มีนาที → null → ตอนเพิ่มคิว UI จะ default 60 และเลือกปรับได้
- ตอนเพิ่มคิว duration เริ่มจากค่าของเมนู แล้วปรับรายคิวได้ (30/45/60/90/120)
  — ไม่ต้องสร้างหน้าแก้เมนูใหม่ (YAGNI)

## หน้า `/queue` — คิววันนี้

### โครงหน้า

- หัวเรื่อง "คิววันนี้" + วันที่ไทย + สรุป: หมอว่างตอนนี้ x คน · คิวรอ y
- ปุ่ม "+ เพิ่มคิว" (ใหญ่ แตะง่าย)
- บอร์ด timeline:
  - แกนนอน = เวลา 10:00–22:00 (OPEN_HOURS เดิม) ช่องละ 15 นาที เลื่อนซ้ายขวาได้
  - แถวแรก "ยังไม่ระบุหมอ" ไว้พักคิว · ถัดไปหนึ่งแถวต่อหมอ (เฉพาะ status=active)
  - เส้นแนวตั้งสีม่วงบอกเวลาปัจจุบัน อัปเดตทุกนาที · เปิดหน้าแล้ว auto-scroll มาที่เวลาปัจจุบัน
- การ์ดคิว: ยาวตาม duration · โชว์ชื่อเมนู + ชื่อลูกค้า(ถ้ามี) + badge สถานะ
  - สีการ์ดตามสถานะ: รอ = ขาวขอบเทา · กำลังนวด = ม่วงอ่อน · ชำระแล้ว = เขียวอ่อน · ยกเลิกไม่แสดง
  - การ์ดซ้อนเวลากันในแถวเดียวกัน → ขอบส้มเตือน (ไม่บล็อก — เผื่อร้านตั้งใจ เช่นนวดคู่)

### การโต้ตอบ (แท็บเล็ตเป็นหลัก)

- **แตะการ์ดสั้น** → dialog รายละเอียด: ปุ่มตามสถานะ
  (รอ→เริ่มนวด · กำลังนวด→เก็บเงิน · ทุกสถานะ→แก้ไข/ยกเลิก)
- **กดค้าง ~300ms แล้วลาก** → ยกการ์ด: ลากขึ้นลงย้ายหมอ · ซ้ายขวาเลื่อนเวลา
  snap ทีละ 15 นาที · ปล่อยแล้วบันทึกทันที
  (ต้องกดค้างก่อนเพื่อไม่ชนกับการเลื่อนบอร์ด — แตะเลื่อนธรรมดา = scroll)
- **+ เพิ่มคิว** → dialog: หมอ (ปุ่มกดแบบหน้า POS รวมตัวเลือก "ยังไม่ระบุ") ·
  เมนู (dropdown เดิม) · ลูกค้า (CustomerPicker เดิม ไม่บังคับ) ·
  เวลาเริ่ม (default = ตอนนี้ ปัดขึ้น 15 นาที) · ระยะเวลา (default จากเมนู)

### อัปเดตสดข้ามเครื่อง

Supabase Realtime subscribe ตาราง `queue_entries` — มีการเปลี่ยนแปลงจากเครื่องไหน
บอร์ดทุกเครื่องดึงข้อมูลใหม่ (refetch ทั้งวัน ไม่ patch รายแถว — ข้อมูลวันละไม่กี่สิบแถว เอาถูกไว้ก่อน)

## เชื่อมหน้า POS

1. ปุ่ม "เก็บเงิน" บนการ์ด → ไป `/pos?queue={id}`
2. หน้า POS (server) โหลด queue entry → ส่ง initial values ให้ `PosForm`:
   therapist, service, customer (id+ชื่อ+เบอร์) — พนักงานเลือกแค่ช่องทางจ่าย/ส่วนลด
3. `createSale` รับ `queue_entry_id` (ไม่บังคับ) — บันทึกขายสำเร็จแล้ว
   อัปเดตคิวเป็น `paid` + ผูก `sale_id` ใน transaction เดียวกัน
4. ถ้าเข้าหน้า POS ตรงๆ แบบเดิม (ไม่ผ่านคิว) ทุกอย่างทำงานเหมือนเดิมทุกประการ
