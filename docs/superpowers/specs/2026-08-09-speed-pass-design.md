# Speed Pass — ยกเครื่องความเร็วทั้งระบบ — Design

**วันที่:** 9 ส.ค. 2569
**สถานะ:** implement ครบ 3 เฟสแล้ว — ผลวัดอยู่ใน docs/ops/speed-pass-measurements.md

## เป้าหมาย

แก้ปัญหา "โหลดหน้าช้าทั่วทั้งระบบ" โดยเฉพาะบนมือถือ — ให้ทุกการกดเมนู
เห็นการตอบสนอง (skeleton) ภายใน ~100ms และเนื้อหาจริงขึ้นภายใน ~1 วินาทีบน 4G
โดย**ไม่แตะกติกาธุรกิจใดๆ ทั้งสิ้น** — งานนี้คือการจัดจังหวะการโหลด ไม่ใช่การแก้ feature

Speed Pass เป็นโปรเจกต์แรกจาก 4 โปรเจกต์ที่วางแผนไว้
(ถัดไป: Boss Hub → Intraday Pulse → Ask สุขกายา) — เป็นฐานให้โปรเจกต์อื่นทั้งหมด

## สาเหตุความช้าที่วิเคราะห์พบ

| # | สาเหตุ | รายละเอียด |
|---|---|---|
| 1 | layout block ทุกหน้า | `src/app/(app)/layout.tsx` รอ `getMyProfile()` (auth.getUser → อ่าน profiles = 2 round trip เรียงกัน) แล้วค่อยยิงอีก 3 query พร้อมกัน (นับคิว pending, วันเกิดวันนี้, เตือนรายจ่าย) — รวม ~3 จังหวะรอเรียงกัน **ก่อน HTML จะออกทุกหน้า ทุกคลิก** |
| 2 | ไม่มี `loading.tsx` เลย | ระหว่างรอ server กดเมนูแล้วจอนิ่งสนิท ไม่มี feedback — รู้สึกช้ากว่าความเป็นจริงมาก |
| 3 | แทบไม่มี Suspense/streaming | แต่ละหน้ารอ query ทั้งหมดเสร็จก่อนแสดงผลทีเดียว ทั้งที่บางส่วนมาทีหลังได้ |
| 4 | query ซ้ำกับข้อมูลกึ่งนิ่ง | รายชื่อหมอนวด/เมนูบริการ/ตั้งค่า ถูกอ่านซ้ำแทบทุกหน้า ทั้งที่เปลี่ยนแค่ตอน admin แก้ |

ข้อเท็จจริงสำคัญ: Vercel (`sin1`) กับ Supabase (`ap-southeast-1`) อยู่สิงคโปร์ทั้งคู่ —
latency ต่อ round trip ต่ำอยู่แล้ว ปัญหาคือ**จำนวนจังหวะรอที่เรียงต่อกัน** ไม่ใช่ระยะทาง

## แนวทางที่เลือก

พิจารณา 3 ทาง: (1) Streaming-first อย่างเดียว (2) Streaming + Cache (3) รื้อเปลือกเป็น SPA
**เลือกทาง 2** — ครบในรอบเดียวโดยไม่รื้อโครงสร้าง ทาง 3 ถูกตัดเพราะรื้อเยอะเกินประโยชน์ (YAGNI)

## ส่วนที่ 1: ยกเครื่อง Layout — จาก ~5 round trip เหลือ ~2

### RPC เดียว `layout_bootstrap()`

สร้าง Postgres function รวมข้อมูลที่ layout ต้องใช้ทั้งหมดไว้ในการเรียกครั้งเดียว:

- โปรไฟล์ผู้ใช้ปัจจุบัน (id, email, full_name, role) — กติกาเดียวกับ `getMyProfile()`
  รวมข้อควรระวังเรื่อง admin อ่าน profiles ได้หลายแถว (ต้องกรอง `auth.uid()` เสมอ)
- จำนวนคิว pending — **นับทุกรายการไม่กรองวัน** (กติกาเดิม: กันรายการค้างข้ามวันหายจากป้าย)
- ลูกค้าวันเกิดวันนี้ที่ยังไม่อวยพร — กติกาเดียวกับ `birthdayTodayCustomers()` ที่หน้า `/crm` ใช้
- เตือนรายจ่ายค้างบันทึก — กติกาเดียวกับ `expenseReminders()`

ฟังก์ชันเป็น `SECURITY INVOKER` — วิ่งใต้ RLS ของผู้เรียกตามปกติ ไม่เปิดสิทธิ์เพิ่ม
รับ parameter `p_today` (วันที่ในเขตเวลาร้าน คำนวณจากฝั่งแอปด้วย `todayInShopTz()` เหมือนเดิม)

โค้ด TypeScript เดิม (`crm-birthday.ts`, `expense-reminders.ts`) **ยังอยู่ที่เดิม**
ให้หน้า `/crm` และงาน cron ใช้ต่อ — SQL ใน RPC ต้องให้ผลตรงกับของเดิมทุกกรณี (มี test เทียบ)

### เปลือกขึ้นก่อน กระดิ่งตามมา

- layout รอแค่ auth + `layout_bootstrap()` (2 round trip) เพื่อรู้ role แล้ววาดเมนู + header ทันที
- ตัวเลขกระดิ่ง/ป้ายเมนู (คิวค้าง, วันเกิด, เตือนรายจ่าย) ห่อ Suspense — streaming ตามมา
  โดย `QueueNotificationsProvider` รับค่าเริ่มแบบ async แทนการ block ทั้ง layout
- realtime subscription ของกระดิ่งทำงานเหมือนเดิมทุกอย่าง

### สิ่งที่ไม่เปลี่ยน

กติกาธุรกิจทั้งหมดเหมือนเดิมเป๊ะ: นับคิวไม่กรองวัน, กติกาวันเกิดเดียวกับ `/crm`,
กติกาเตือนรายจ่ายเดิม, เสียง/toast แจ้งเตือนเดิม — แค่ย้ายที่คำนวณและจัดจังหวะโหลดใหม่

## ส่วนที่ 2: Skeleton ทุกหน้า + Cache ข้อมูลกึ่งนิ่ง

### 2a. `loading.tsx`

- **skeleton เฉพาะทาง** หน้าที่ใช้บ่อยสุด: `today` (โครงตาราง), `pos` (โครงฟอร์ม),
  `queue` (โครงบอร์ด), `overview` (โครงการ์ดตัวเลข)
- **skeleton กลาง** (component ใช้ร่วม) สำหรับหน้าที่เหลือ: history, crm, customers,
  expenses, finance, insights, reports, members, shifts, team, commission, settings, more
- โทนสี skeleton ตามธีมร้าน (น้ำตาล `#664343` จางๆ บนพื้นครีม) ไม่ใช่เทา default

### 2b. Cache แบบ tag-based

| ข้อมูล | tag | invalidate เมื่อ |
|---|---|---|
| รายชื่อหมอนวด `therapists` | `therapists` | บันทึกเพิ่ม/แก้/พักงานที่หน้า team/settings |
| เมนูบริการ+ราคา `services` | `services` | บันทึกแก้เมนู/ราคาที่ settings |
| ตั้งค่าร้าน `settings` | `settings` | บันทึกตั้งค่า |

- invalidate ผูกกับ server action ที่กดบันทึกโดยตรง (revalidate tag) —
  **ไม่ใช้เวลาหมดอายุ** จึงไม่มีทางเห็นข้อมูลเก่า
- ข้อมูลที่เปลี่ยนตลอด (ยอดขาย, บิล, คิว, ลูกค้า, รายจ่าย, คอมมิชชั่น) **ไม่ cache เลย**
- cache แยกตาม role ไม่ได้ปนกัน (ข้อมูล 3 กลุ่มนี้ staff อ่านได้อยู่แล้วตาม RLS จึงไม่มีประเด็นข้อมูลรั่วข้าม role
  แต่ต้อง review จุดนี้ตอน implement อีกครั้ง)

### 2c. เก็บกวาด query หน้า top 5

ไล่ตรวจ `today`, `pos`, `overview`, `history`, `queue` — จุดที่ `await` เรียงกัน
ทั้งที่ไม่พึ่งพากัน จับรวม `Promise.all` (เช่น `pos/page.tsx` มี await เดี่ยวหลายจุด)

### ข้อบังคับเรื่อง Next.js 16

ตาม AGENTS.md — โปรเจกต์นี้ใช้ Next.js 16 ที่ API เปลี่ยนจากรุ่นเก่า
**ก่อนเขียนโค้ดต้องอ่าน guide ใน `node_modules/next/dist/docs/`** โดยเฉพาะเรื่อง
caching (`"use cache"` + `cacheTag`/`cacheLife` หรือ API ที่เอกสารระบุ) และ loading/streaming
ห้ามเดา API จากความจำรุ่นเก่า

## ส่วนที่ 3: การวัดผล การทดสอบ และลำดับการปล่อย

### วัดผลก่อน-หลัง

- วัด baseline ก่อนแก้: เวลาตั้งแต่ request จนได้ HTML (TTFB) และจนเห็นเนื้อหา
  ของ 5 หน้าหลัก — บันทึกตัวเลขไว้ในสเปกนี้หรือ log ของ implementation plan
- วัดซ้ำหลังจบแต่ละเฟส เทียบกับ baseline — พิสูจน์ด้วยตัวเลข ไม่ใช่ความรู้สึก

**เป้า:** เห็น skeleton ภายใน ~100ms หลังกดเมนู · เนื้อหาจริงภายใน ~1s บนมือถือ 4G

### การทดสอบ

- test เทียบผล RPC `layout_bootstrap()` กับ logic TypeScript เดิม — ผลต้องตรงกันทุกกรณี
  รวม edge case: วันเกิด 29 ก.พ., คิว pending ค้างข้ามวัน, ผู้ใช้ที่ไม่มี profile (allowlist ไม่ผ่าน)
- test ว่า server action บันทึกตั้งค่า/หมอนวด/บริการ สั่ง revalidate tag จริง
- test เดิมทั้งหมดผ่าน (`npm run test`) และ `npm run lint` ผ่าน

### ลำดับการปล่อย — 3 เฟส แยก deploy อิสระ

| เฟส | เนื้องาน | ความเสี่ยง |
|---|---|---|
| 1 | `loading.tsx` + skeleton ทั้งหมด | ต่ำมาก — ไม่แตะ logic ใดๆ |
| 2 | RPC `layout_bootstrap()` + streaming กระดิ่ง | กลาง — ย้าย logic ไป SQL (กันด้วย test เทียบผล) · migration ผ่าน MCP `apply_migration` + เก็บสำเนาลง `supabase/migrations/` ตามกติกา README |
| 3 | cache กึ่งนิ่ง + `Promise.all` หน้า top 5 | ต่ำ–กลาง — invalidate ผูกปุ่มบันทึกตรงๆ |

เฟสไหนมีปัญหา revert เฉพาะเฟสนั้นได้โดยไม่กระทบเฟสอื่น

### ความเสี่ยงหลักที่ระบุไว้

จุดเสี่ยงสุดคือย้าย logic วันเกิด/เตือนรายจ่ายไป SQL (เฟส 2) —
กันด้วย test เทียบผลตรงกับของเดิมก่อนสลับใช้จริง และโค้ดเดิมยังอยู่ให้ย้อนกลับได้ทันที
