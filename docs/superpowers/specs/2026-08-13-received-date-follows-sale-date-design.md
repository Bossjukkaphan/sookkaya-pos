# วันเงินเข้าของบิลขายต้องเป็นวันที่ให้บริการ ไม่ใช่วันที่กดคีย์

**วันที่:** 2026-08-13
**สถานะ:** อนุมัติแล้ว รอลงมือ

## ที่มา

วันที่ 13 ส.ค. 2026 เทียบเงินเข้าของวันนั้นกับ ThaiHand แล้วต่างกัน 550 บาท
(เรา QR 8,610 · ThaiHand QR 8,060)

ต้นเหตุคือบิล `SK-20260802-029` (ลูกค้านิกกี้ · นวดแผนไทย 90 นาที · 550 ฿) ซึ่งเป็น**งานของวันที่
2 ส.ค.** แต่พนักงานเพิ่งมาคีย์เข้าระบบวันที่ 13 ส.ค. ระบบบันทึก `bill_payments.received_date`
เป็นวันที่กดคีย์ เงิน 550 บาทจึงไปโผล่ในยอดเงินเข้าของวันที่ 13 แทนที่จะเป็นวันที่ 2

ยอดขายและรายได้ถูกต้องอยู่แล้ว — บิลอยู่ในยอดของวันที่ 2 ส.ค. ตามที่ควร กระทบเฉพาะการ์ด
"เงินเข้าบัญชี" ว่าเงินก้อนนั้นนับอยู่วันไหน

## สภาพปัจจุบัน

ระบบเขียน `received_date` อยู่ **2 ที่ และความหมายต่างกันคนละเรื่อง**

| ที่ | สถานการณ์ | ค่าที่เขียน | ถูกหรือผิด |
|---|---|---|---|
| `src/app/(app)/sale-actions.ts:396` (`createSale`) | ลูกค้าจ่ายตอนใช้บริการ | `todayInShopTz()` | **ผิด** เมื่อบิลลงวันย้อนหลัง |
| `src/app/(app)/payment-actions.ts:31` (`addBillPayment`) | ลูกค้าค้างไว้แล้วกลับมาจ่ายทีหลัง | `todayInShopTz()` | ถูกแล้ว |

`updateSale` ไม่แตะบรรทัดชำระเลย และคง `sale_date` เดิมเสมอ (`sale-actions.ts:846`)
ส่วน `deleteSale` แค่ลบบรรทัดทิ้งกัน orphan — ทั้งสองทางไม่เกี่ยวกับปัญหานี้

**บิลจะลงวันย้อนหลังได้ทางเดียวคือผูกกับการ์ดคิวของวันนั้น** — `saleDate` ตั้งต้นเป็นวันนี้ แล้วถูก
แทนที่ด้วย `queue_entries.queue_date` เมื่อบิลผูกกับคิว (`sale-actions.ts:197-205`) ระบบจึงรู้
วันที่ถูกต้องอยู่ในมือแล้ว ไม่ต้องถามพนักงาน

**ขนาดของปัญหา:** ไล่ `bill_payments` ทั้งตารางตลอดกาลแล้วพบแถวที่ `received_date <> sale_date`
**เพียงแถวเดียว** คือบิลนิกกี้นี่เอง แปลว่ากลไกบิลค้างรับยังไม่เคยถูกใช้ข้ามวันจริงสักครั้ง
ความต่างที่เคยเกิดในระบบนี้มีแต่บั๊กตัวนี้ตัวเดียว

## ข้อเท็จจริงหน้าร้านที่ใช้ตัดสิน

Boss ยืนยัน 13 ส.ค. 2026: เวลาคีย์บิลย้อนหลัง **ลูกค้าจ่ายเงินวันที่มาใช้บริการเสมอ**
กรณีที่ลูกค้าค้างเงินไว้จริงมีทางของตัวเองอยู่แล้ว คือคีย์เป็นบิลค้างรับแล้วกดปุ่มเก็บเงินทีหลัง
ซึ่ง `addBillPayment` ประทับวันที่กดอย่างถูกต้อง

## ทางเลือกที่พิจารณา

**ก. ให้ `createSale` ใช้ `saleDate`** ← เลือกทางนี้
แก้บรรทัดเดียว ไม่แตะโมเดลข้อมูล ไม่แตะบิลค้างรับ ระบบมีคำตอบอยู่แล้วจากการ์ดคิว

**ข. ถามพนักงานว่ารับเงินวันไหนตอนคีย์ย้อนหลัง**
ไม่เลือก เพราะคำตอบจะเหมือนเดิมทุกครั้งตามข้อเท็จจริงข้างบน เท่ากับเพิ่มขั้นตอนตอนพนักงานกำลังรีบ
เพื่อข้อมูลที่ระบบรู้อยู่แล้ว และเปิดช่องให้กดผิดใหม่

**ค. เลิกใช้ `received_date` ให้เงินเข้านับตาม `sale_date` ล้วน ๆ**
ไม่เลือก เพราะเท่ากับทิ้งความสามารถบิลค้างรับที่ทำไว้ครบแล้ว (`v_bill_due` · ปุ่มเก็บเงิน ·
หน้าประวัติบิล) วันที่ลูกค้าค้างเงินจริงแล้วกลับมาจ่ายอาทิตย์หน้า เงินก้อนนั้นควรขึ้นวันที่ได้รับจริง
ไม่ใช่ย้อนไปวันที่นวด ไม่งั้นดูสภาพคล่องไม่ได้ · และต้องรื้อ view กับหน้าจอหลายจุดโดยไม่จำเป็น

## สิ่งที่จะทำ

### 1. โค้ด

`src/app/(app)/sale-actions.ts:396` เปลี่ยนค่าที่เขียนลง `received_date` จาก `todayInShopTz()`
เป็น `saleDate` พร้อมคอมเมนต์ภาษาไทยที่อธิบายสองเรื่อง:

- ทำไมที่นี่ต้องใช้วันของบิล (ลูกค้าจ่ายตอนใช้บริการ · บิลย้อนหลังมาจากการ์ดคิวของวันนั้น)
- ทำไม `payment-actions.ts` ยังต้องใช้ `todayInShopTz()` ต่อไป (คนละสถานการณ์: ค้างไว้แล้วมาจ่ายทีหลัง)

คอมเมนต์ข้อหลังสำคัญ เพราะถ้าไม่เขียนไว้ คนที่มาเห็นสองที่เขียนไม่เหมือนกันจะ "แก้ให้ตรงกัน"
แล้วพังอีกด้านหนึ่งแทน

### 2. เทสต์ (กันชนตัวจริง)

**ข้อ 1-2 เพิ่มใน `src/app/(app)/sale-actions.test.ts`** (ไฟล์มีอยู่แล้ว แต่ตัว fake ปัจจุบันครอบเฉพาะ
เส้นทางเครดิตหมดอายุ ยังไม่เคยแตะ `bill_payments` เลย ต้องขยาย fake ให้รองรับตาราง `bill_payments`
และให้ `queue_entries` คืน `queue_date` ย้อนหลังได้ แล้วดักแถวที่ถูก insert ไว้ตรวจ)

1. ปิดบิลที่ผูกกับการ์ดคิวย้อนหลัง → `bill_payments.received_date` ต้องเท่ากับวันของคิว **ไม่ใช่วันนี้**
2. ปิดบิลของวันนี้ → `received_date` ต้องเป็นวันนี้ (กันแก้แล้วทำของเดิมพัง)

**ข้อ 3 สร้างไฟล์ใหม่ `src/app/(app)/payment-actions.test.ts`** (ยังไม่มีไฟล์เทสต์ของ action นี้เลย)

3. กดเก็บเงินบิลค้างรับผ่าน `addBillPayment` → `received_date` ต้องเป็นวันนี้เสมอ **แม้บิลจะเป็นของวันก่อน**

ข้อ 3 คือข้อที่กันคนไปแก้ผิดที่ในอนาคต จึงต้องมีถึงแม้จะต้องตั้งไฟล์ใหม่

### 3. แก้ข้อมูลเก่า 1 แถว

```sql
update bill_payments
   set received_date = '2026-08-02'
 where id = 'ec1e837d-e564-4dbd-bfe6-bcce34b14e47';
-- แถวนี้คือบรรทัดชำระของบิล SK-20260802-029 (ลูกค้านิกกี้ · QR Code · 550 ฿)
-- ยืนยัน id จากฐานข้อมูลแล้ว 13 ส.ค. 2026 — ตอนร่างสเปกเคยใส่ id ของบิลอาลีผิดมาก่อน
-- ต้อง select ยืนยันก่อน update เสมอ อย่าคัดลอก id จากเอกสาร
```

**ระบุด้วย id ตรง ๆ ห้ามใช้ UPDATE แบบกวาดทั้งตาราง** เพราะวันข้างหน้าถ้าร้านเริ่มใช้บิลค้างรับจริง
แถวเหล่านั้น**ควร**มี `received_date` ต่างจาก `sale_date` การกวาดจะไปทำลายข้อมูลที่ถูกต้อง

ต้องอ่าน id จริงจากฐานข้อมูลก่อนรัน ไม่ใช่เดา

**ผลที่คาดหวัง:** เงินเข้าวันที่ 13 ส.ค. จาก 10,380 เหลือ **9,830** (QR 8,060 ตรงกับ ThaiHand)
และเงินเข้าวันที่ 2 ส.ค. เพิ่มขึ้น 550

## สิ่งที่จงใจไม่ทำ

**ไม่เพิ่มข้อตรวจใน `supabase/reconciliation.sql`** — เงื่อนไขที่จับบั๊กนี้ได้คือ
`received_date > sale_date` ซึ่งเป็นสภาพที่**ถูกต้อง**สำหรับบิลค้างรับ ถ้าใส่เข้าไปจะกลายเป็น
สัญญาณเตือนลวงทันทีที่ร้านเริ่มใช้ฟีเจอร์นั้นจริง เทสต์ข้อ 1-3 ทำหน้าที่นี้ได้ตรงกว่าและไม่มีผลข้างเคียง

**ไม่แตะ `member_topups.topup_date`** — การเติมเงินบันทึกวันที่กดอยู่แล้ว และลูกค้าเติมเงินต่อหน้า
พนักงานเสมอ ไม่มีการคีย์ย้อนหลัง

## Global Constraints

- ยอด `ยอดรับจริง (Volume)` และ `รายรับที่รับรู้` ห้ามเปลี่ยนแม้แต่บาทเดียว — งานนี้ขยับเฉพาะ
  "เงินเข้าบัญชี" ว่าอยู่วันไหน
- วันที่ทุกที่ใช้เขตเวลากรุงเทพผ่าน `todayInShopTz()` หรือ `(now() at time zone 'Asia/Bangkok')::date`
  ห้ามใช้ `current_date` หรือ `new Date()` ดิบ
- คอมเมนต์เป็นภาษาไทย · ชื่อตัวแปรเป็นภาษาอังกฤษ
- แก้ข้อมูลจริงต้องระบุ id เท่านั้น ห้าม UPDATE แบบไม่มีเงื่อนไขเจาะจง
- ขึ้น production: `git fetch && git rebase origin/main && git push` แล้วสั่ง `vercel deploy --prod`
  เอง — การ push เข้า main **ไม่ได้** deploy อัตโนมัติ (ยืนยันแล้ว 13 ส.ค. 2026)
