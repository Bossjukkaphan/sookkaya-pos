# รู้จักลูกค้า (Customer Insights) — Design

**วันที่:** 21 ส.ค. 2569 · **สถานะ:** รออนุมัติ

## เป้าหมาย

เจ้าของร้านอยากรู้จักลูกค้าตัวเอง: เพศอะไร อายุเท่าไร จำนวนเท่าไร ใช้บริการอย่างไร —
โดย**ไม่เพิ่มภาระพนักงานหน้าร้านเลย** (ทางเลือก ก ที่เจ้าของร้านเลือก 21/8/2569)

| ข้อมูล | มีแล้ว | จากทั้งหมด |
|---|---|---|

บทสรุปเชิงดีไซน์สองข้อ:

1. **ท่อเก็บข้อมูลผ่านไลน์ทำงานดีอยู่แล้ว** — หน้าแต้ม (`/book/points`) บังคับกรอกโปรไฟล์
   (ชื่อ, วันเกิด*, เพศ*) ก่อนใช้ ด้วย `ProfileForm` เดิม คนที่ผ่านหน้านี้กรอกครบ 64%
   คอขวดจริงคือ**จำนวนคนที่ไปถึงหน้านั้น** ไม่ใช่ฟอร์ม
2. **ข้อมูลวันนี้ยังไม่แทนภาพรวม** (8%) — หน้าวิเคราะห์ใดๆ ต้องประกาศความครอบคลุม
   ตรงๆ เสมอ ห้ามปล่อยกราฟที่ดูน่าเชื่อถือทั้งที่ฐานข้อมูลบาง

## ส่วนที่ 1: ตัวเร่งเก็บข้อมูล (ฝั่งลูกค้าใน LIFF)

**หลักการ: ไม่สร้างฟอร์มใหม่ — เพิ่มแค่ "ทางเข้า" ไปยังฟอร์มเดิมของหน้าแต้ม**
(`/book/points` เช็ค `profileComplete` แล้วบังคับ `ProfileForm` เองอยู่แล้ว)

นิยาม "โปรไฟล์ครบ" ใช้ของเดิมเป๊ะ: `Boolean(birthday && gender)`
(`points-actions.ts:79`) — ห้ามเขียนนิยามที่สอง

ทางเข้าใหม่ 2 จุด แสดงเฉพาะเมื่อผูกไลน์แล้วและโปรไฟล์ยังไม่ครบ:

1. **หน้าจอง (`/book` wizard)** — หลังส่งคำขอจองสำเร็จ (สถานะ done) แสดงการ์ดชวน
   ใต้ข้อความยืนยัน: หัวข้อทำนอง "กรอกโปรไฟล์ 1 นาที รับสิทธิ์แต้มสะสม 🌿"
   ลิงก์ไป `/book/points` · ผู้ใช้ที่โปรไฟล์ครบแล้วไม่เห็นการ์ดนี้เลย
2. **หน้าการจองของฉัน (`/book/mine`)** — แถบชวนแบบเดียวกันเหนือรายการจอง
   เงื่อนไขการแสดงเหมือนกัน

ข้อมูลสถานะโปรไฟล์ฝั่ง client: ใช้ผลจาก action ที่หน้านั้นเรียกอยู่แล้วถ้ามีข้อมูลพอ
หรือเพิ่ม field ในผลลัพธ์ของ action เดิม — **ห้ามเพิ่ม round trip ใหม่ต่างหาก**
(ขัดหลัก Speed Pass) รายละเอียดให้ตัดสินตอนเขียนแผนโดยยึดข้อห้ามนี้

การ์ดชวนพลาด/โหลดไม่ได้ → ไม่แสดงเงียบๆ ห้ามกระทบการจอง

**นอกขอบเขตโค้ด:** ป้าย QR หน้าเคาน์เตอร์ ("ผูกไลน์ สะสมแต้ม จองคิวได้") เป็นงาน ops
ทำหลังโปรเจกต์นี้จบ

## ส่วนที่ 2: แท็บ "กลุ่มลูกค้า" — คำตอบของ "อยู่เมนูไหน"

**ตำแหน่ง: ดูแลลูกค้า (`/crm`) → แท็บวิเคราะห์ (`?tab=insights`) → sub-tab ใหม่
`sub=demo` ("กลุ่มลูกค้า")** ข้าง LTV/หายไปนาน · สิทธิ์ `canSeeInsights`
(ผู้จัดการ+เจ้าของร้าน) ตามแท็บวิเคราะห์เดิม

ประชากรที่วิเคราะห์: **ลูกค้าที่มีบิลใน 90 วันล่าสุด** (ตายตัว ไม่มีตัวเลือกช่วง — YAGNI
รอเฟส 2) นับจาก `sales.customer_id` (บิลไม่ระบุชื่อไม่อยู่ในประชากร แต่รายงานจำนวนไว้)

เรียงจากบนลงล่าง:

### 2.1 การ์ดความครอบคลุม (บนสุดเสมอ — ห้ามย้าย)

"ลูกค้าที่ใช้บริการ 90 วัน N คน · รู้เพศ x% · รู้อายุ y%" พร้อมแถบ progress สองแถบ
ถ้า x หรือ y < 30% → ป้ายเตือนสีเหลือง: ตัวเลขด้านล่างมาจากลูกค้าส่วนน้อย
อาจไม่แทนภาพรวมร้าน (แสดงข้อมูลตามปกติ ไม่ซ่อน — แต่ผู้อ่านต้องรู้ข้อจำกัดก่อนเห็นกราฟ)

### 2.2 แจกแจง 3 มิติ: เพศ · ช่วงอายุ · สัญชาติ

แต่ละมิติเป็นตารางกลุ่มละแถว คอลัมน์: จำนวนคน · ยอดใช้จ่ายรวม (90 วัน) ·
เฉลี่ย/คน · จำนวนครั้งเฉลี่ย — สี่ตัวนี้เริ่มตอบ "พฤติกรรมการใช้บริการ" ตั้งแต่วันแรก

- ช่วงอายุ: ต่ำกว่า 20 / 20-29 / 30-39 / 40-49 / 50-59 / 60+ คำนวณจาก `birthday`
  เทียบวันที่ปัจจุบันเขตเวลาร้าน
- **"ไม่ทราบ" เป็นแถวหนึ่งของทุกมิติเสมอ ห้ามซ่อน** — เห็นทั้งภาพและช่องว่างพร้อมกัน
- ยอดใช้จ่ายใช้กติการายได้กลางของระบบ: `coalesce(revenue_recognize, net_amount)`

### 2.3 การ์ดความคืบหน้าการเก็บข้อมูล (ท้ายหน้า)

"ผูกไลน์แล้ว N คน · โปรไฟล์ครบ M คน" — ไว้ตามดูว่าตัวเร่งในส่วนที่ 1 ทำงานจริงไหม
เทียบกับ baseline 21/8/2569: ผูกไลน์ 140 / ครบ 90

## ส่วนที่ 3: เทคนิค

- **ไม่มี migration ไม่แตะฐานข้อมูล** — server component ดึงบิล 90 วัน
  (`sale_date, customer_id, net_amount, revenue_recognize`) + ลูกค้า
  (`id, gender, birthday, nationality`) แล้วคำนวณใน TypeScript
- แกนคำนวณเป็นฟังก์ชันบริสุทธิ์ใน `src/lib/` (เช่น `demographics.ts`):
  `ageBucket(birthday, today)` และตัวแจกแจงต่อมิติ — เขียนเทสต์ก่อน (TDD) ครอบ:
  ขอบช่วงอายุพอดี (อายุ 20, 30, ...), ลูกค้าไม่มีวันเกิด/เพศ → "ไม่ทราบ",
  ลูกค้าหลายบิลนับคนเดียวแต่ยอดรวมทุกบิล, เฉลี่ยเมื่อกลุ่มว่าง (ไม่ NaN),
  วันเกิด 29 ก.พ.
- บิล 90 วันมีเพดานแถวของ PostgREST (1,000) — ต้องดึงแบบไม่โดนตัดเงียบ
  (บทเรียนจากบั๊กหน้ารายงาน 16/8/2569) วิธีการให้กำหนดในแผน
- แท็บพัง → error ขังในแท็บตามแพตเทิร์นเดิม ไม่ลามหน้าดูแลลูกค้าหลัก
- เทสต์เดิมทั้งหมดผ่าน + `npm run lint` + `npm run build`

## เกณฑ์ตรวจรับ

1. จองคิวสำเร็จโดยโปรไฟล์ไม่ครบ → เห็นการ์ดชวน · โปรไฟล์ครบ → ไม่เห็น
2. `/book/mine` แสดงแถบชวนตามเงื่อนไขเดียวกัน
3. แท็บ "กลุ่มลูกค้า" แสดงครบ 3 บล็อก การ์ดความครอบคลุมอยู่บนสุด
   และเปอร์เซ็นต์ตรงกับข้อมูลจริง (ตรวจเทียบ SQL ตรงๆ อย่างน้อย 1 ครั้ง)
4. แถว "ไม่ทราบ" ปรากฏในทุกมิติเมื่อมีข้อมูลไม่ครบ
5. พนักงาน (role staff) มองไม่เห็นแท็บนี้และเข้า URL ตรงไม่ได้
6. เทสต์ใหม่ของฟังก์ชันแจกแจงผ่านครบ + เทสต์เดิมผ่านหมด

## นอกขอบเขต (เฟส 2 — เริ่มเมื่อความครอบคลุมเพศ ≥ ~40-50%)

- เมนูโปรด/ประเภทบริการต่อกลุ่ม · ความถี่กลับมาเชิงลึก · เปรียบเทียบข้ามช่วงเวลา
- ตัวเลือกช่วงเวลาในแท็บกลุ่มลูกค้า
- การเก็บข้อมูลโดยพนักงาน (ทางเลือก ข ที่ไม่ได้เลือก)
