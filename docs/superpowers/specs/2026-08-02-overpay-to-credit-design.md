# ปุ่ม "เก็บเป็นเครดิต" — ย้ายยอดเกินรับของบิลไปเป็นเครดิตลูกค้า

**เป้าหมาย:** บิลที่รับเงินเกิน (ลูกค้าจ่ายล่วงหน้าแล้วใช้บริการไม่ครบ) พนักงานกดปุ่มเดียวจบ — ระบบลดบรรทัดชำระให้เท่ายอดบิล แล้วออกใบ "เครดิตคงเหลือ" ให้ลูกค้าใช้ครั้งหน้า โดยเงินเข้าของวันนั้นรวมไม่เปลี่ยน

**ที่มา:** เคสคุณซี 2 ส.ค. 2026 (โอน 1,500 จอง 120 นาที 2 คิว ใช้จริง 60 นาที 2 คิว) แก้มือผ่านฐานข้อมูลไปแล้ว · migration `allow_leftover_credit_tier` เพิ่ม tier `เครดิตคงเหลือ` ไว้แล้ว

## กติกาการตัดสิน (สำคัญที่สุด)

ยอดเกินรับเกิดได้ 4 สาเหตุ แต่**มีแค่บางสาเหตุที่ควรกลายเป็นเครดิต**:

| สาเหตุ | ทางแก้ที่ถูก |
|---|---|
| จ่ายล่วงหน้า ใช้ไม่ครบ / แก้เมนูเป็นตัวถูกลงหลังเก็บเงิน | ✅ เก็บเป็นเครดิต |
| คีย์ยอดรับผิด | ❌ ต้องแก้ยอดรับ (ลบ/แก้บรรทัดชำระ) |
| คืนเงินสดให้ลูกค้าไปแล้ว | ❌ ต้องบันทึกเงินคืน |

กล่องจึง**ถามสาเหตุก่อนเสมอ** ห้ามให้ปุ่มเดียวยิงตรงเป็นเครดิต ไม่งั้นพนักงานจะใช้กลบการคีย์ผิด แล้วเครดิตที่ไม่มีเงินจริงรองรับจะงอกในระบบ

รอบแรกทำเฉพาะทาง ✅ — อีกสองทางแสดงเป็นคำแนะนำว่าให้ไปแก้ที่ไหน (ลบบรรทัดชำระในหน้าบิล) ยังไม่สร้างกลไกเงินคืน

## เงื่อนไข (ทุกข้อต้องผ่าน)

1. **สิทธิ์** — เฉพาะ `admin` / `manager` (แบบเดียวกับ `deleteBillPayment` — เงินก้อนนี้กลายเป็นหนี้ที่ร้านค้างลูกค้า)
2. **ยอดเกินขั้นต่ำ 100 บาท** — ต่ำกว่านั้นถือเป็นเศษ/ทิป ไม่ออกใบเครดิต (กันใบเครดิตเศษๆ รกระบบ)
3. **บิลต้องผูกลูกค้า** — `sales.customer_id` ของบิลต้องไม่ว่าง และทุกใบในบิลต้องเป็นลูกค้าคนเดียวกัน ไม่งั้นไม่รู้จะให้เครดิตใคร
4. **ห้ามมีเครดิตในบิล** — `credit_total > 0` ปฏิเสธ (จ่ายด้วยเครดิตแล้วเกิน = ต้องคืนเข้าเครดิตเดิม ไม่ใช่ออกใบใหม่ ไม่งั้นนับเงินซ้ำ)
5. **วันที่ใบเครดิต = วันที่รับเงินจริง** (`received_date` ล่าสุดของบิล) ไม่ใช่วันที่กดปุ่ม — ไม่งั้นเงินเข้าเด้งข้ามวัน งบรายวันเพี้ยนย้อนหลัง
6. **อ่าน due สดจาก `v_bill_due`** ตอนกดยืนยัน (ห้ามเชื่อค่าที่ส่งมาจากหน้าจอ)

## สิ่งที่ระบบทำเมื่อกดยืนยัน

1. ลดบรรทัดชำระของบิลลงรวม = ยอดเกิน — ไล่ลดจากบรรทัดล่าสุดก่อน · บรรทัดที่เหลือ 0 ให้ลบทิ้ง
2. `insert member_topups` — `tier='เครดิตคงเหลือ'`, `cash_received = credit_added = ยอดเกิน`, `bonus_added = 0`, `payment_method` = วิธีของบรรทัดที่ถูกลด, `expiry_date` = +12 เดือน, `notes` อ้างอิงบิล
3. **ไม่** เปลี่ยน `customers.customer_type` เป็นสมาชิก · **ไม่** ให้แต้ม (แต้มได้ไปแล้วตอนจ่ายค่าบริการ)
4. revalidate `/today` `/queue` `/history` `/members` `/customers/[id]`

ผลลัพธ์: `due` ของบิล = 0 · เงินเข้าวันนั้นรวมเท่าเดิม (ย้ายจากช่องค่าบริการไปช่องเติมเครดิต) · ด่าน `bill_overpaid` ยังเป็น 0

## UI

- ป้ายส้ม "เกินรับ N ฿" ใน `due-badge.tsx` เพิ่มปุ่ม **"เก็บเป็นเครดิต"** ข้างป้าย (เดิม due<0 ไม่มีปุ่มเลย)
- ปุ่มโผล่เฉพาะเมื่อผ่านเงื่อนไขเบื้องต้น (สิทธิ์ + ยอด ≥ 100) — ไม่ผ่านให้เห็นแค่ป้ายเหมือนเดิม
- กดแล้วเปิดกล่อง: เลือกสาเหตุ → ทางเครดิตโชว์สรุป (ชื่อลูกค้า · ยอด · วันหมดอายุ) → ยืนยัน
- เงื่อนไขที่รู้ได้เฉพาะฝั่ง server (ลูกค้าไม่ผูก / มีเครดิตในบิล) ตอบกลับเป็น error ในกล่อง

## ทดสอบ

- unit (vitest): กติกาขั้นต่ำ · การไล่ลดบรรทัดชำระจากล่าสุด (ลดพอดี / ต้องข้ามหลายบรรทัด / บรรทัดเหลือ 0)
- action test แบบ mock: ปฏิเสธเมื่อ role ไม่ถึง · บิลไม่มีลูกค้า · บิลมีเครดิต · ยอดต่ำกว่าขั้นต่ำ · due ไม่ติดลบแล้ว
- E2E มือ: สร้างบิลทดสอบรับเกิน → กดปุ่ม → due=0 · ใบเครดิตขึ้นในโปรไฟล์ลูกค้า · เงินเข้าวันนั้นไม่เปลี่ยน → ลบข้อมูลทดสอบ

## ไม่ทำรอบนี้

กลไกคืนเงินสด · เครดิตหมดอายุแล้วรับรู้เป็นรายได้ร้าน (ช่องว่างเดิมของแพ็กเกจสมาชิกด้วย) · แก้ยอดรับจากในกล่องนี้ (ให้ไปลบบรรทัดชำระที่หน้าบิลตามเดิม)
