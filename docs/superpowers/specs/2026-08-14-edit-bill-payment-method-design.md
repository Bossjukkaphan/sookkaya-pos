# แก้ช่องทางชำระเงินของบิลขายได้จากหน้ายอดวันนี้

**วันที่:** 2026-08-14
**สถานะ:** อนุมัติแล้ว รอเขียนแผน

## ที่มา

พนักงานกดช่องทางชำระเงินผิดตอนปิดบิล แล้วแก้ไม่ได้ ต้องมาขอให้แก้ทางฐานข้อมูลทีละใบ
(เกิดจริงกับบิลลูกค้า "อาลี" 9 ส.ค. 2026 ที่ลูกค้าจ่าย WeChat แต่ถูกคีย์เป็นบัตรเครดิต
กว่าจะรู้ตัวคือตอนเอาไปเทียบกับ ThaiHand หลายวันให้หลัง)

## สภาพปัจจุบัน

**ปุ่มช่องทางในกล่องแก้บิลมีอยู่แล้ว แต่ถูกล็อกทั้งแถบเมื่อบิลมีบรรทัดชำระ**
(`src/app/(app)/today/edit-sale-dialog.tsx:426` — `disabled={payments.length > 0 || ...}`)

การล็อกนั้นถูกต้อง: ช่องทางจริงของบิลถูกกำหนดโดย `bill_payments` ส่วน `sales.payment_method`
เป็นเพียงป้ายสรุป ถ้าปล่อยให้แก้เฉพาะหัวบิล ข้อมูลสองที่จะไม่ตรงกันและข้อตรวจ
`tracked_bill_method_mismatch` ใน `supabase/reconciliation.sql` จะ FAIL ทันที

`updateSale` เขียน `sales.payment_method` ได้ แต่**ไม่เคยแตะ `bill_payments` เลย** —
นั่นคือเหตุผลที่ต้องล็อก ไม่ใช่ความบกพร่อง

**ทางแก้ที่ระบบแนะนำอยู่ตอนนี้เป็นอันตรายแล้ว** ข้อความใต้กล่องบรรทัดชำระ
(`edit-sale-dialog.tsx:713-716`) บอกให้ *"ลบบรรทัดแบ่งจ่ายก่อน (เฉพาะหัวหน้า)"* แล้วเก็บเงินใหม่
แต่ `addBillPayment` ประทับ `received_date = todayInShopTz()` เสมอ ดังนั้นการลบแล้วเก็บใหม่
กับบิลของเมื่อวานจะ **ย้ายเงินมาโผล่วันนี้** ซึ่งเป็นบั๊กตัวเดียวกับที่เพิ่งแก้ไปเมื่อ 13 ส.ค. 2026
(ดู `docs/superpowers/specs/2026-08-13-received-date-follows-sale-date-design.md`) แต่เข้าทางประตูหลัง

**ข้อมูลจริง ณ 14 ส.ค. 2026:** บรรทัดชำระ 198 แถวจาก 193 บิล — 188 บิลมีบรรทัดเดียว ·
5 บิลแบ่งจ่าย 2 บรรทัด (2.6%) เคสบรรทัดเดียวจึงเป็นเคสหลักที่ต้องทำให้ง่ายที่สุด
แต่เคสแบ่งจ่ายคือเคสที่พังง่ายที่สุดถ้าออกแบบผิด

## ขอบเขต

**ทำ**

1. เพิ่ม server action แก้ `bill_payments.method` ของบรรทัดเดียว พร้อม sync `sales.payment_method`
2. เพิ่มปุ่ม "แก้ช่องทาง" ที่แต่ละบรรทัดในกล่อง "บรรทัดชำระของบิล"
3. เพิ่มคอลัมน์บันทึกผู้แก้ใน `bill_payments`
4. เก็บกวาด `accounting-window.ts` ให้ชื่อฟังก์ชันไม่ผูกกับคำว่า "รายจ่าย"

**ไม่ทำ**

- ไม่ปลดล็อกแถบปุ่มช่องทางด้านบนของกล่องแก้บิล (เหตุผลอยู่ในหัวข้อทางเลือก)
- ไม่แตะยอดเงิน วันเงินเข้า หรือ `bill_key` ของบรรทัดชำระ
- ไม่เปลี่ยนกติกาของปุ่มแก้ช่องทางในใบเติมเงินสมาชิก (ยังแก้ย้อนหลังได้ไม่จำกัดเดือน)
- ไม่แตะ `addBillPayment` และ `deleteBillPayment`

## Global Constraints

- ยอดเงินทุกตัวห้ามขยับ — งานนี้เปลี่ยนเฉพาะ "ป้ายช่องทาง" ของเงินที่รับมาแล้ว
- ช่องทางที่เลือกได้คือ `REAL_MONEY_METHODS` จาก `@/lib/constants` เท่านั้น
  (`เงินสด · QR Code · บัตรเครดิต · E-Wallet`) ห้ามพิมพ์ชื่อช่องทางด้วยมือที่ไหนทั้งสิ้น
- วิธีหลักของบิลคำนวณด้วย `primaryMethod()` จาก `@/lib/payments` **ห้ามเขียนสูตรใหม่**
- กติกาวันปิดงบอยู่ที่ `src/lib/accounting-window.ts` ที่เดียว **ห้ามเขียนเงื่อนไขเดือนซ้ำที่อื่น**
- วันที่ใช้เวลาไทยผ่าน `todayInShopTz()` เสมอ
- คอมเมนต์และข้อความบนหน้าจอเป็นภาษาไทย · ชื่อตัวแปรเป็นภาษาอังกฤษ
- migration ใช้ MCP `apply_migration` แล้วเก็บสำเนาลง `supabase/migrations/` ห้ามรัน `supabase db push`
- ขึ้น production: push เข้า main แล้วสั่ง `vercel deploy --prod` เอง — push ไม่ deploy ให้อัตโนมัติ

## ทางเลือกที่พิจารณา

**ก. แก้ที่บรรทัดชำระโดยตรง** ← เลือกทางนี้
แก้ตรงจุดที่เก็บความจริง ใช้รูปแบบหน้าจอเดียวกับปุ่มแก้ช่องทางในประวัติเติมเงินที่ทำไปแล้ว
รองรับบิลแบ่งจ่ายได้เองโดยไม่ต้องมีเงื่อนไขพิเศษ

**ข. ปลดล็อกแถบปุ่มด้านบนแล้วให้ `updateSale` ไล่แก้บรรทัดตาม**
ไม่เลือก เพราะพังกับบิลแบ่งจ่าย — บิลที่จ่ายบัตร 650 + QR 240 จะ sync ไม่ได้โดยไม่ทำลาย
ข้อมูลการแบ่งจ่าย ต้องเขียนเงื่อนไข "ปลดล็อกเฉพาะบิลบรรทัดเดียว" ซึ่งอธิบายบนหน้าจอยาก
และทำให้ `updateSale` (ฟังก์ชันที่ใหญ่และเสี่ยงอยู่แล้ว) รับผิดชอบเพิ่มอีกเรื่อง

**ค. คงทางเดิม (ลบแล้วเก็บใหม่) แต่แก้ `addBillPayment` ให้ใช้วันของบิล**
ไม่เลือก เพราะ `addBillPayment` มีไว้สำหรับเงินที่เพิ่งได้รับจริง การบังคับให้ใช้วันบิล
จะพังเคสบิลค้างรับที่ลูกค้ากลับมาจ่ายทีหลัง ซึ่งเป็นเหตุผลทั้งหมดที่ฟีเจอร์นั้นมีอยู่

## ส่วนที่ 1 — เก็บกวาด `accounting-window.ts`

ไฟล์นี้มีกติกาวันปิดงบอยู่แล้ว (`canEditExpenseOn` · `CLOSE_GRACE_DAYS = 3`) และเป็นกติกาที่
Boss เลือกให้ใช้กับบิลขายด้วย แต่ตอนนี้ชื่อฟังก์ชันผูกกับคำว่า "รายจ่าย" และคอมเมนต์หัวไฟล์
เขียนไว้ว่า *"บิลขายกับใบเติมเงินสมาชิกยังใช้กติกาเดิม (เฉพาะเดือนปัจจุบัน)"* ซึ่งกำลังจะไม่จริง

**ทำ:**

- แยกตัวตัดสินจริงออกมาเป็น `canEditClosedBookRecordOn(recordDate: string, today: string): boolean`
  โดยย้ายเนื้อในของ `canEditExpenseOn` มาทั้งดุ้น ไม่แก้ตรรกะแม้แต่บรรทัดเดียว
- `canEditExpenseOn` คงไว้ เรียกต่อไปยังฟังก์ชันใหม่ — ผู้เรียกเดิม (`expense-actions.ts:28`)
  และข้อความ error เฉพาะทางของฝั่งรายจ่ายไม่กระทบ
- แก้คอมเมนต์หัวไฟล์ให้ตรงความจริงใหม่: รายจ่ายและ**ช่องทางชำระของบิลขาย**ใช้หน้าต่างนี้ ·
  การแก้บิลขายเรื่องอื่น (`updateSale`/`deleteSale`) ยังเป็นเฉพาะเดือนปัจจุบัน ·
  **ใบเติมเงินสมาชิกไม่จำกัดเดือน** พร้อมเหตุผลของแต่ละอย่าง
- `CLOSE_GRACE_DAYS` ยังคงเดิม ไม่แตะ (`payout-periods.ts:53` ใช้อยู่)

เทสต์เดิมใน `src/lib/accounting-window.test.ts` ต้องผ่านเหมือนเดิมทุกข้อ
เพิ่มเทสต์ว่า `canEditExpenseOn` กับ `canEditClosedBookRecordOn` ให้ผลตรงกันเสมอ

## ส่วนที่ 2 — Server action `updateBillPaymentMethod`

อยู่ใน `src/app/(app)/payment-actions.ts` (ไฟล์เดียวกับ `addBillPayment`/`deleteBillPayment`)

```
updateBillPaymentMethod(paymentId: string, method: string)
  → Promise<{ ok: true } | { ok: false; error: string }>
```

**ลำดับการทำงาน**

1. ตรวจ `method` ต้องอยู่ใน `REAL_MONEY_METHODS` — ไม่ผ่านคืน error **ก่อนแตะฐานข้อมูล**
   ข้อความประกอบจาก `REAL_MONEY_METHODS.join(" / ")`
2. อ่านบรรทัดชำระตาม `paymentId` (`id, bill_key`) — ไม่พบคืน `"ไม่พบบรรทัดชำระนี้"`
3. อ่านบิลของ `bill_key` เพื่อเอา `sale_date` — ไม่พบคืน `"ไม่พบบิลของบรรทัดชำระนี้"`
4. ตรวจหน้าต่างปิดงบด้วย `canEditClosedBookRecordOn(sale_date, todayInShopTz())`
   ไม่ผ่านคืนข้อความที่บอกทั้งเหตุผลและกำหนด เช่น
   `"บิลเดือน 2026-06 ปิดงบแล้ว — แก้ช่องทางของเดือนก่อนหน้าได้ถึงวันที่ 3 ของเดือนถัดไปเท่านั้น"`
5. เขียน `bill_payments` แถวนั้น: `method` · `edited_by` · `edited_at`
   ใช้ `.select("id").maybeSingle()` แล้วถ้าไม่ได้แถวกลับมาให้คืน error
   (RLS ปฏิเสธแบบเงียบจะได้ไม่ถูกรายงานว่าสำเร็จ — บทเรียนจาก `updateTopupPaymentMethod`)
6. อ่านบรรทัดชำระ**ทั้งหมด**ของ `bill_key` ใหม่หลังแก้ แล้วหาวิธีหลักด้วย `primaryMethod()`
7. เขียน `sales.payment_method` ของ **ทุกแถวที่อยู่ในบิลเดียวกัน**
   (`coalesce(bill_id, id) = bill_key` — ฝั่ง PostgREST ใช้ `.or("bill_id.eq.<key>,id.eq.<key>")`
   แบบเดียวกับที่ `deleteSale` ทำใน `sale-actions.ts:605`) พร้อมตั้ง `edited_by`
8. `revalidatePath` ครอบคลุม `/today` · `/reports` · `/history` · `/queue` · `/overview`

**ห้ามแตะ** `amount` · `received_date` · `received_at` · `bill_key` · `created_by`

**ไม่ตรวจ role** — พนักงานทุกคนแก้ได้ตามที่ Boss เลือก ต่างจาก `deleteBillPayment` ที่จำกัด
admin/manager เพราะการลบทำให้บิลกลายเป็นค้างรับ (เงินหายจากยอดเงินเข้า) แต่การแก้ช่องทาง
ไม่ขยับยอดใดเลย และ `edited_by` เป็นตัวตามรอย

## ส่วนที่ 3 — Migration

`supabase/migrations/20260814100000_bill_payments_edit_audit.sql`

```sql
alter table public.bill_payments add column if not exists edited_by text;
alter table public.bill_payments add column if not exists edited_at timestamptz;
```

พร้อม `comment on column` ภาษาไทยอธิบายว่าใช้บันทึกคนที่แก้ช่องทางล่าสุด
เป็นการเพิ่มคอลัมน์ nullable ล้วน ไม่กระทบแถวเดิม 198 แถว (193 บิล)

หลัง apply ต้อง generate `src/types/database.ts` ใหม่ แล้ว**ใส่คอมเมนต์หัวไฟล์สี่บรรทัดกลับเข้าไป**
ก่อน `export type Json =` เพราะ generator ไม่ใส่ให้:

```ts
/**
 * Types สร้างจาก Supabase schema
 * อัปเดตใหม่ด้วย: npx supabase gen types typescript --project-id jrioyrmicioqammeevgh
 */
```

## ส่วนที่ 4 — หน้าจอ

แก้ `src/app/(app)/today/edit-sale-dialog.tsx` ในกล่อง "บรรทัดชำระของบิล" (บรรทัด 663-717)

- แต่ละบรรทัดเพิ่มปุ่ม "แก้ช่องทาง" ขนาดเล็กข้างปุ่มลบ กดแล้วกางปุ่ม `REAL_MONEY_METHODS`
  ทั้ง 4 ตัวใต้บรรทัดนั้น เลือกแล้วเปลี่ยนทันที ไม่ต้องยืนยันสองจังหวะ
  (กดผิดกดใหม่ได้ ไม่มีข้อมูลเสียหาย — ต่างจากปุ่มลบ)
- กางแผงของบรรทัดหนึ่งต้องปิดแผงของบรรทัดอื่น และต้องไม่ทำให้ปุ่มลบค้างสถานะยืนยัน
  (บทเรียนจากหน้าประวัติเติมเงิน: สองปุ่มที่ถือ state คนละก้อนต้องปลดกันเอง
  ไม่งั้นการยืนยันสองจังหวะของปุ่มลบจะถูกข้าม)
- เลือกช่องทางเดิมซ้ำ = ปิดแผงเฉย ๆ ไม่ยิง action
- ล้มเหลว = `toast.error` พร้อมข้อความจาก server และเปิดแผงค้างไว้ · สำเร็จ = `toast.success` +
  `router.refresh()`
- แถบปุ่มช่องทางด้านบน (บรรทัด 411-445) **คงล็อกไว้เหมือนเดิม ไม่แตะ**
- เปลี่ยนข้อความบรรทัด 713-716 จาก *"หากต้องการเปลี่ยนช่องทางการชำระเงิน กรุณาลบบรรทัดแบ่งจ่ายก่อน
  (เฉพาะหัวหน้า)"* เป็นบอกว่ากดปุ่มแก้ช่องทางที่บรรทัดได้เลย ไม่ต้องลบ — **คำแนะนำเดิมต้องหายไป**
  เพราะการลบแล้วเก็บใหม่จะย้ายวันเงินเข้ามาเป็นวันนี้

`payments` ที่ส่งเข้ามาเป็น prop อยู่แล้ว (`BillPaymentLine[]` มี `id`) จึงไม่ต้องแก้ฝั่ง
`today/page.tsx` และ `history/page.tsx`

## ส่วนที่ 5 — เทสต์

เพิ่มใน `src/app/(app)/payment-actions.test.ts` (ไฟล์มีอยู่แล้ว มี fake supabase ให้ต่อยอด)

1. แก้ช่องทางของบิลบรรทัดเดียว → `bill_payments.method` เปลี่ยน และ `sales.payment_method` เปลี่ยนตาม
2. **ชุดคีย์ที่เขียนลง `bill_payments` ต้องเป็น `method` · `edited_by` · `edited_at` เท่านั้น**
   ตรวจด้วย `expect(Object.keys(patch).sort()).toEqual([...])` — เป็น whitelist ไม่ใช่ blacklist
   (ถ้าวันหนึ่งมีคนเพิ่มคอลัมน์เข้า patch เทสต์ต้องแดงทันที)
3. บิลชุดหลายแถว → `sales.payment_method` ต้องถูกอัปเดตครบทุกแถวของบิล ไม่ใช่แถวเดียว
4. บิลแบ่งจ่าย 2 บรรทัด แก้บรรทัด**เล็ก** → วิธีหลักของบิลต้องไม่เปลี่ยน
5. บิลแบ่งจ่าย 2 บรรทัด แก้บรรทัด**ใหญ่** → วิธีหลักของบิลต้องเปลี่ยนตาม
6. ช่องทางที่ไม่รู้จักถูกปฏิเสธก่อนแตะฐานข้อมูล (`from` ต้องไม่ถูกเรียกเลย)
7. ไม่พบบรรทัดชำระ → คืน error ไม่เขียนอะไร
8. บิลของเดือนที่ปิดงบแล้ว → คืน error และไม่เขียนอะไร
9. บิลของเดือนก่อนหน้าในวันที่ยังไม่พ้นวันผ่อนผัน → แก้ได้

เทสต์ข้อ 8-9 ต้องตรึง "วันนี้" ด้วย mock ของ `@/lib/datetime` ให้ผลคงที่ไม่ขึ้นกับวันที่รันจริง

ตอนกระทบยอดข้ามเดือน ถ้าล็อกจะแก้ไม่ได้เลย ส่วนบิลขายเป็นเงินหน้าร้านที่ต้องปิดงบตามรอบปกติ
**ความไม่สมมาตรนี้ตั้งใจ อย่า "แก้ให้เหมือนกัน" โดยไม่ถาม Boss ก่อน**

**ไม่เพิ่มข้อตรวจใหม่ใน `reconciliation.sql`** — `tracked_bill_method_mismatch` ที่มีอยู่แล้ว
คือด่านที่เฝ้าเรื่องนี้ตรงตัว ถ้า action เขียน `sales.payment_method` ไม่ครบทุกแถวมันจะจับได้เอง
