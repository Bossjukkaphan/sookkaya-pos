# แก้ช่องทางรับเงินเป็นทรานแซกชันเดียว — design

วันที่ 14 ตุลาคม 2569 · ต่อยอดจาก [2026-08-14-edit-bill-payment-method-design.md](2026-08-14-edit-bill-payment-method-design.md)

## ปัญหา

ปุ่ม "แก้ช่องทาง" ที่บรรทัดรับเงินเขียนสองจังหวะแยกกัน: แก้ `bill_payments` ก่อน
แล้วค่อย sync ป้ายหัวบิล `sales.payment_method` ตามบรรทัดยอดสูงสุด — ถ้าจังหวะสองล้ม
(เน็ตหลุด/สิทธิ์/ปิดแอป) สองตารางค้างไม่ตรงกัน หน้าจอสั่งให้ "กดใหม่อีกครั้ง"
แต่พนักงานมักปิดข้อความโดยไม่กดซ้ำ

เกิดจริง 2 บิลติดกัน (เจอจากด่าน `tracked_bill_method_mismatch` เมื่อ 14/10/2569):
คุณตี๋ 13/10 (บรรทัดถูกแก้เป็น QR แต่หัวบิลค้าง "เงินสด") และพั้นซ์ 14/10
(บรรทัดถูกแก้เป็นบัตรเครดิต แต่หัวบิลค้าง "QR Code") — เจ้าของร้านสั่งให้รวมสองจังหวะ
เป็นก้อนเดียว

## สิ่งที่ทำ

- migration `20261014060000_update_bill_payment_method_rpc.sql` — ฟังก์ชัน
  `update_bill_payment_method(p_payment_id, p_method, p_edited_by)`:
  แก้บรรทัด → หาวิธีหลัก (บรรทัดยอดสูงสุด กติกาเดียวกับ `primaryMethod()` ใน
  `lib/payments.ts`) → อัปเดตทุกแถว `sales` ของบิล — **ในทรานแซกชันเดียว**
  จังหวะไหนล้ม (รวม RLS ปฏิเสธเงียบ = 0 แถว ซึ่งถูกแปลงเป็น exception)
  ย้อนกลับทั้งหมด ไม่มีสถานะครึ่งเดียว · `security invoker` เดิน RLS ของผู้เรียกเหมือนเดิม
- `payment-actions.ts` — `updateBillPaymentMethod` เหลือ: ด่าน whitelist ช่องทาง ·
  หาบรรทัด/วันที่บิล · หน้าต่างเวลาแก้ไข (เหมือนเดิมทุกข้อ) → เรียก RPC หนึ่งครั้ง ·
  ข้อความ error เปลี่ยนจาก "กรุณากดใหม่อีกครั้ง" เป็น "ยังไม่มีอะไรถูกเปลี่ยน"
  เพราะไม่มีสถานะครึ่งเดียวให้ซ่อมแล้ว
- เทสต์: ด่านก่อนเรียก RPC + การแปล error ยังคุมครบ · เทสต์กติกาวิธีหลัก/บิลชุด
  ของเดิมตัดออกเพราะตรรกะย้ายไป SQL (จุดเสี่ยงเดิมคือรอยต่อระหว่างสองจังหวะ
  ซึ่งตอนนี้ไม่มีรอยต่อแล้ว)

## สิ่งที่ไม่เปลี่ยน

พนักงานทุก role ยังแก้ได้ · หน้าต่างเวลา (เดือนปัจจุบัน + เดือนก่อน) · ห้ามแตะ
amount / received_date / bill_key · ด่าน reconciliation ตัวเดิมยังเฝ้าอยู่

## การตรวจรับ

- เทสต์ action 12 ข้อผ่าน · tsc · eslint
- บน production: เรียก RPC ด้วย id ปลอมต้องได้ exception `LINE_NOT_UPDATED`
  (พิสูจน์ว่าฟังก์ชันอยู่จริงและด่าน 0 แถวทำงาน)
