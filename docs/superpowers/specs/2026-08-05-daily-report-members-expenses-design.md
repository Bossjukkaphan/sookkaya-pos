# สมาชิกใหม่ + รายจ่ายที่บันทึก ในการ์ด Daily Report — Design

ต่อยอดจาก `2026-08-05-line-daily-report-design.md` — เพิ่มสองบล็อกในการ์ดเดิม
ไม่แตะสูตรหรือช่องที่มีอยู่แล้ว

## เป้าหมาย

เจ้าของร้านอ่านการ์ด 22:00 แล้วต้องตอบสองคำถามนี้ได้โดยไม่ต้องเปิดแอป

1. **วันนี้มีคนสมัครสมาชิกใหม่กี่ราย ซื้อแพ็กเกจไหน** — และแยกออกจากคนเก่าที่มาต่ออายุ
2. **วันนี้มีใครคีย์รายจ่ายเข้าระบบเท่าไร** — นับตาม**วันที่บันทึก** ไม่ใช่วันที่ของรายจ่าย

## ทำไมต้องนับตามวันที่บันทึก

นี่คือข้อกำหนดที่เจ้าของร้านย้ำสองครั้ง และข้อมูลจริงพิสูจน์ว่าจำเป็น

| วันที่บันทึก | รายการ | ยอดรวม | ลงย้อนหลัง | ย้อนไกลสุด |
|---|---|---|---|---|
| 5 ส.ค. 2569 | 14 | 55,690 | 13 จาก 14 | 25 พ.ค. |
| 4 ส.ค. 2569 | 1 | 452 | 1 | 3 ส.ค. |
| 3 ส.ค. 2569 | 8 | **207,792** | 8 จาก 8 | 10 ก.ค. |

เงิน 207,792 ที่คีย์เข้ามาวันที่ 3 ส.ค. กระจายไปนั่งอยู่ในเดือน ก.ค. ทั้งก้อน
ถ้าการ์ดนับตาม `expense_date` ยอดนี้จะ**ไม่โผล่ในการ์ดวันไหนเลย** ทั้งที่เป็นวันที่
เกิดเหตุการณ์คีย์ค่ามือหมอซ้ำ 92,025 บาท (ดู commit `1fd8fd2`)

การนับตามวันที่บันทึกทำให้การ์ดกลายเป็นเครื่องมือกำกับดูแล ไม่ใช่แค่รายงานยอดขาย

## สถาปัตยกรรม

ตามโครงเดิมสามชั้น ไม่เปลี่ยนขอบเขตความรับผิดชอบ

| ชั้น | ไฟล์ | หน้าที่ที่เพิ่ม |
|---|---|---|
| สูตร | `src/lib/daily-report.ts` | รับแถวดิบ คืน `memberSignups` และ `expenseEntries` — ฟังก์ชันบริสุทธิ์ ไม่แตะฐานข้อมูล |
| การ์ด | `src/lib/daily-report-flex.ts` | เพิ่มแถวในการ์ด อ่านจาก `DailyReport` อย่างเดียว |
| ท่อ | `src/app/api/cron/daily-report/route.ts` | เพิ่ม query แล้วส่งแถวดิบเข้าสูตร |

## บล็อกสมาชิก

### หน้าตา

```
👥 สมาชิกใหม่     1 ราย · Silver ×1 · 5,000 ฿
🔁 ต่ออายุ        2 ราย · Silver ×2 · 10,000 ฿
                  (รวมอยู่ใน Cash In แล้ว)
```

### นิยาม

- แหล่งข้อมูล: ตาราง `member_topups` คีย์ `topup_date = วันที่รายงาน`
- **สมาชิกใหม่** = ลูกค้าที่แถวของวันนี้เป็น topup **แรกในชีวิต** ของเขา
  (ไม่มีแถว `member_topups` ของ `customer_id` เดียวกันที่ `topup_date` เก่ากว่า)
- **ต่ออายุ** = แถวที่ลูกค้าคนนั้นเคยมี topup มาก่อนแล้ว
- ลูกค้าคนเดียวเติมสองครั้งในวันเดียว → ครั้งแรกนับใหม่ ครั้งที่สองนับต่ออายุ
  (ตัดสินรายแถว ไม่ใช่รายคน) เพราะยอดเงินต้องบวกครบทุกแถว
- **ยอดเงินใช้ `cash_received`** คือเงินสดที่รับจริง ไม่ใช่ `credit_added` ที่บวกโบนัสแล้ว
  โชว์ `credit_added` จะทำให้ตัวเลขสูงกว่าเงินที่เข้าร้านจริง
- แพ็กเกจอ่านจาก `tier` นับจำนวนต่อ tier แล้วเรียงจากมากไปน้อย ยอดเท่ากันเรียงตามชื่อ
  รูปแบบ `Silver ×2 · Gold ×1`

### ตัด tier "เครดิตคงเหลือ" ทิ้ง

ค่าคงที่ `export const EXCLUDED_TIER = "เครดิตคงเหลือ"` ประกาศใน `src/lib/daily-report.ts`
ที่เดียว — แถวที่ `tier` ตรงกับค่านี้ถูกตัดทิ้ง
**ทั้งจากการนับของวันนี้ และจากประวัติที่ใช้ตัดสินว่าใครเป็นสมาชิกใหม่**

เหตุผล: แถวเหล่านี้มาจากฟีเจอร์ overpay-to-credit (ลูกค้าจ่ายเกินแล้วเก็บส่วนเกิน
เป็นเครดิต) ไม่ใช่การซื้อแพ็กเกจ มีอยู่จริงในข้อมูล 2 แถว ยอดรวม 1,020 เมื่อ 2 ส.ค.
ถ้าไม่ตัดจากประวัติด้วย ลูกค้าที่เคยมีเศษเงินเก็บเข้าเครดิตแล้ววันนี้มาซื้อ Silver
จะถูกนับเป็น "ต่ออายุ" ทั้งที่ไม่เคยซื้อแพ็กเกจมาก่อน

### บรรทัดกำกับ "(รวมอยู่ใน Cash In แล้ว)"

บรรทัดนี้บังคับมี ห้ามตัดออกเพื่อความสวยงาม

นิยามของ `v_daily_summary.cash_in` คือ

```sql
cash_in = COALESCE(p.sales_cash, 0) + COALESCE(t.topup_cash, 0)
```

โดย `t.topup_cash = sum(member_topups.cash_received)` — เงินเติมสมาชิกอยู่ใน Cash In
อยู่แล้ว ถ้าโชว์ 5,000 ลอยๆ ผู้บริหารจะเข้าใจว่าเป็นเงินเข้าเพิ่มแล้วบวกซ้ำ

### กรณีพิเศษ

| กรณี | พฤติกรรม |
|---|---|
| ไม่มี topup เลยในวันนั้น (หลังตัด tier ที่ยกเว้น) | ซ่อนทั้งบล็อก รวมบรรทัดกำกับ |
| มีแต่สมาชิกใหม่ ไม่มีต่ออายุ | โชว์เฉพาะแถว "สมาชิกใหม่" |
| มีแต่ต่ออายุ | โชว์เฉพาะแถว "ต่ออายุ" |
| `cash_received` เป็น null | อ่านเป็น 0 ยังนับจำนวนราย |
| `tier` เป็น null หรือค่าว่าง | แสดงเป็น `ไม่ระบุ` ในรายการแพ็กเกจ |

## บล็อกรายจ่ายที่บันทึก

### หน้าตา

```
🧾 บันทึกรายจ่ายวันนี้   14 รายการ · 55,690 ฿
   ย้อนหลัง 13 · 55,232 ฿
   พ.ค. 4,548 · มิ.ย. 24,884 · ก.ค. 25,800
```

บรรทัด "ย้อนหลัง" และบรรทัดแยกเดือนใช้สีส้มเตือน (`BRAND.gold`) เมื่อมีรายการย้อนหลัง

### นิยาม

- แหล่งข้อมูล: ตาราง `expenses`
- **วันที่บันทึก** = `(created_at AT TIME ZONE 'Asia/Bangkok')::date`
  ฝั่งโค้ดกรองด้วยช่วงเวลา UTC เพื่อให้ index บน `created_at` ทำงาน
  `created_at >= '<วันที่รายงาน>T00:00:00+07:00'` และ `< '<วันถัดไป>T00:00:00+07:00'`
- **ลงย้อนหลัง** = `expense_date < วันที่บันทึก`
- **ลงล่วงหน้า** (`expense_date > วันที่บันทึก`) นับรวมในยอดรวม แต่ไม่นับเป็นย้อนหลัง
  และไม่แยกเดือน — ของจริงแทบไม่เกิด แต่ต้องไม่ทำให้ตัวเลขเพี้ยน
- แยกเดือนนับเฉพาะรายการย้อนหลัง เรียงเดือนเก่าไปใหม่ ใช้ชื่อเดือนไทยย่อ

### กรณีพิเศษ

| กรณี | พฤติกรรม |
|---|---|
| ไม่มีการบันทึกรายจ่ายเลยในวันนั้น | ซ่อนทั้งบล็อก |
| มีบันทึกแต่ไม่มีรายการย้อนหลัง | โชว์แค่บรรทัดแรก ไม่โชว์บรรทัดย้อนหลังและบรรทัดแยกเดือน |
| ย้อนหลังหลายเดือนเกิน 4 เดือน | เลือก 4 เดือนที่**ยอดสูงสุด** แล้ว**เรียงเก่าไปใหม่**ตอนแสดง ยอดของเดือนที่เหลือรวมเป็นก้อนเดียวต่อท้ายว่า `· อื่นๆ <ยอดบาท>` (เป็นยอดเงิน ไม่ใช่จำนวนเดือน) |
| `amount` เป็น null | อ่านเป็น 0 ยังนับจำนวนรายการ |

### ข้อจำกัดที่รู้ตัวและยอมรับแล้ว

1. **แยกไม่ออกว่าใครเป็นคนบันทึก** — ตาราง `expenses` ไม่มีคอลัมน์ผู้ทำรายการ
   รายการที่เกิดจาก migration ของนักพัฒนาจึงปนกับรายการที่พนักงานคีย์
   ตัวอย่างจริง: ยอด 4,548 (พ.ค.) และ 24,884 (มิ.ย.) ของวันที่ 5 ส.ค. มาจาก migration
   แก้ข้อมูลตกหล่น ไม่ใช่พนักงาน การแยกให้ออกต้องเพิ่มคอลัมน์ก่อน — คนละงาน ไม่ทำรอบนี้
2. **ช่องโหว่เวลา** — การ์ดยิงราว 22:00 รายการที่คีย์หลังจากนั้นจะไปโผล่การ์ดวันถัดไป
   ข้อมูลไม่หาย แต่ช้าไปหนึ่งวัน ยอมรับได้เพราะร้านปิดก่อนเที่ยงคืน
3. **ไม่เกี่ยวกับกำไรขั้นต้นในการ์ด** — กำไรขั้นต้น = รายรับ − ค่ามือ ยังไม่หักรายจ่ายอื่น
   บล็อกนี้เป็นข้อมูลกำกับดูแลล้วน ห้ามเอาไปลบกับกำไรที่โชว์

## ชนิดข้อมูล

เพิ่มใน `src/lib/daily-report.ts`

```ts
export type TierCount = { tier: string; count: number }

export type MemberSignups = {
  newCount: number
  newCash: number
  newTiers: TierCount[]
  renewCount: number
  renewCash: number
  renewTiers: TierCount[]
}

export type ExpenseEntries = {
  count: number
  total: number
  backdatedCount: number
  backdatedTotal: number
  /** เฉพาะรายการย้อนหลัง เลือก 4 เดือนยอดสูงสุดแล้วเรียงเก่าไปใหม่
   *  month เป็นชื่อเดือนไทยย่อ เช่น "มิ.ย." */
  byMonth: { month: string; total: number }[]
  /** ยอดรวมของเดือนที่ถูกตัดออกจาก byMonth — 0 เมื่อไม่มีเดือนถูกตัด */
  otherMonthsTotal: number
}
```

แถวดิบที่สูตรรับเข้า

```ts
export type TopupRow = {
  customer_id: string
  tier: string | null
  cash_received: number | null
}

export type TopupHistoryRow = {
  customer_id: string
  topup_date: string
}

export type ExpenseEntryRow = {
  expense_date: string
  amount: number | null
  /** วันที่บันทึกตามเวลาไทย รูปแบบ YYYY-MM-DD — route แปลงมาให้แล้ว */
  recorded_date: string
}
```

เพิ่มใน `DailyReportInput`

```ts
  topups: TopupRow[]
  topupHistory: TopupHistoryRow[]
  expenseEntries: ExpenseEntryRow[]
```

เพิ่มใน `DailyReport`

```ts
  memberSignups: MemberSignups
  expenseEntries: ExpenseEntries
```

`empty: true` (วันที่ไม่มีบิลเลย) ยังคงย่อการ์ดเหลือหัวกับปุ่มเหมือนเดิม
สองบล็อกนี้ไม่แสดง แม้จะมีข้อมูล — เพื่อไม่ให้ขัดกับกติกาที่มีอยู่

## การดึงข้อมูลใน route

เพิ่มใน `Promise.all` เดิม สองรายการ

```ts
supabase
  .from("member_topups")
  .select("customer_id, tier, cash_received")
  .eq("topup_date", today),
supabase
  .from("expenses")
  .select("expense_date, amount, created_at")
  .gte("created_at", `${today}T00:00:00+07:00`)
  .lt("created_at", `${tomorrow}T00:00:00+07:00`),
```

จากนั้น **เฉพาะวันที่มี topup** ยิงอีกหนึ่ง query เพื่อดูประวัติ

```ts
const ids = [...new Set(topups.data?.map((r) => r.customer_id) ?? [])]
const history = ids.length
  ? await supabase.from("member_topups").select("customer_id, topup_date").in("customer_id", ids)
  : { data: [], error: null }
```

query ที่สองขึ้นกับผลของ query แรกจึงต้องรอ — วันที่ไม่มีคนเติมเลยจะไม่ยิงเลย
ทางเลือกที่ทำ view `v_member_first_topup` ไว้ตัดรอบนี้ทิ้ง เพราะต้องเพิ่ม migration
เพื่อประหยัด round trip ที่เกิดไม่กี่ครั้งต่อวัน — แลกไม่คุ้ม

`recorded_date` แปลงในตัว route ก่อนส่งเข้าสูตร ให้สูตรยังบริสุทธิ์
ใช้ `Intl.DateTimeFormat` timezone `Asia/Bangkok` แบบเดียวกับ `todayInShopTz`

### การกันพัง

query ใหม่ทั้งสามเข้าไปอยู่ในรายการ `failed` เดิมที่เช็ค `r.error?.message`
ถ้าอันไหนพัง route ตอบ `{ ok: false }` และ**ไม่ส่งการ์ด** ตามกติกาเดิม —
ตัวเลขไม่ครบดีกว่าส่งการ์ดผิดเข้ากลุ่มผู้บริหาร

## โครงสร้าง Flex ที่เพิ่ม

ใช้ `opRow(label, value, color)` ที่มีอยู่แล้ว ไม่สร้าง helper ใหม่

ลำดับใน `opsRows`

1. `👥 Sessions` (เดิม)
2. `💼 ค่ามือรวม` (เดิม)
3. `🏆 TOP หมอ` (เดิม มีเงื่อนไข)
4. **`👥 สมาชิกใหม่`** (ใหม่ มีเงื่อนไข)
5. **`🔁 ต่ออายุ`** (ใหม่ มีเงื่อนไข)
6. **บรรทัดกำกับ `(รวมอยู่ใน Cash In แล้ว)`** ขนาด `xxs` สี `BRAND.textMuted` โผล่คู่กับข้อ 4-5
7. `📅 MTD` (เดิม)
8. `🗓 คิวจองพรุ่งนี้` (เดิม)
9. **`🧾 บันทึกรายจ่ายวันนี้`** (ใหม่ มีเงื่อนไข)
10. **บรรทัดย้อนหลัง + บรรทัดแยกเดือน** ขนาด `xxs` สี `BRAND.gold` `wrap: true`

บล็อก Action alerts ยังอยู่ท้ายสุดเหมือนเดิม

ห้ามใช้ property ที่ LINE ไม่รู้จัก — เคยเจอ `letterSpacing` ทำการ์ดไม่ขึ้นมาแล้ว
(commit `7e8b520`) property ที่ใช้ได้ต้องมีอยู่ในการ์ดปัจจุบันแล้วเท่านั้น

### `src/lib/daily-report.test.ts` (เพิ่มจาก 21 เทสเดิม)

สมาชิก
1. ลูกค้าไม่เคยเติมมาก่อน → นับเป็นใหม่
2. ลูกค้าเคยเติมเมื่อเดือนก่อน → นับเป็นต่ออายุ
3. ลูกค้าคนเดียวเติมสองครั้งวันเดียว → ใหม่ 1 ต่ออายุ 1 ยอดเงินครบทั้งสองแถว
4. tier `เครดิตคงเหลือ` ถูกตัดจากการนับ
5. tier `เครดิตคงเหลือ` ในประวัติไม่ทำให้คนซื้อ Silver ครั้งแรกกลายเป็นต่ออายุ
6. หลาย tier ในวันเดียว → เรียงจากมากไปน้อย
7. `cash_received` null → นับราย ยอดเป็น 0
8. `tier` null → แสดง `ไม่ระบุ`
9. ไม่มี topup เลย → ทุกช่องเป็น 0 และอาร์เรย์ว่าง

รายจ่าย
10. รายการลงตรงวัน → ไม่นับย้อนหลัง
11. รายการลงย้อนหลัง → นับทั้งยอดรวมและยอดย้อนหลัง
12. ย้อนหลังข้ามสามเดือน → `byMonth` เรียงเก่าไปใหม่ครบสามเดือน
13. ย้อนหลังเกินสี่เดือน → เหลือสี่เดือนยอดสูงสุด บวกยอดรวมของที่เหลือ
14. `expense_date` มากกว่าวันบันทึก → นับยอดรวม ไม่นับย้อนหลัง
15. `amount` null → นับรายการ ยอดเป็น 0

## สิ่งที่ไม่ทำรอบนี้ (YAGNI)

- ชื่อลูกค้าในการ์ด — เจ้าของร้านเลือกยอดรวมล้วน กลุ่มผู้บริหารมีหลายคน
- คอลัมน์ผู้บันทึกรายจ่าย — ต้อง migration และแก้ทุกจุดที่เขียน `expenses`
- Action alert เมื่อมีรายจ่ายย้อนหลังผิดปกติ — การ์ดจำกัด alert ไว้ 3 ข้อ
  ถ้าเพิ่มต้องตัดของเดิมออก รอดูของจริงสักพักก่อนค่อยตัดสิน
- แยกยอดตามหมวดรายจ่าย — หน้า `/insights/expenses` ทำได้ดีกว่าอยู่แล้ว
- นับสมาชิกที่หมดอายุหรือเครดิตหมดในวันนั้น — คนละเรื่องกับการสมัคร
