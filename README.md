### Migration ทำผ่าน MCP ไม่ได้ทำผ่าน Supabase CLI

โปรเจกต์นี้แก้ schema ด้วย **Supabase MCP ยิงตรงเข้าโปรเจกต์จริง** ทุกครั้ง
ไม่เคยใช้ CLI workflow (`supabase link` / `db push` / `db reset`) เลยแม้แต่ครั้งเดียว

- **ประวัติตัวจริงอยู่ในฐานข้อมูล** ที่ตาราง `supabase_migrations.schema_migrations`
  ตารางนั้นคือคำตอบสุดท้ายว่าตอนนี้ schema เป็นอย่างไร
- **`supabase/migrations/` เก็บสำเนาของทุก migration** (ครบทั้ง 34 ตัว
  ชื่อไฟล์ `<version>_<name>.sql` ตรงกับที่ MCP บันทึกไว้) มีไว้ให้อ่าน ให้ review
  และให้ `git diff` เห็นว่าแต่ละครั้งแก้อะไร — ไม่ใช่ไฟล์ที่ระบบเอาไปรันเอง
  ถ้าไม่เก็บไว้ คนที่มาทีหลังจะอ่านโค้ดแล้วไม่มีทางรู้เลยว่าฐานข้อมูลหน้าตายังไง

> **ห้ามรัน `supabase db push` หรือ `supabase db reset` ใส่ environment จริง
> ก่อนถามเจ้าของร้านก่อน** — เพราะโปรเจกต์ไม่เคยเดินสาย CLI มาก่อน
> สถานะฝั่ง CLI จึงไม่ตรงกับของจริง สองคำสั่งนี้อาจล้างข้อมูลขายทั้งหมดทิ้งได้
> ถ้าจะแก้ schema ให้ใช้ MCP `apply_migration` แล้ว **เก็บสำเนาไฟล์ลงโฟลเดอร์นี้ด้วยทุกครั้ง**

### สร้างบัญชีผู้ใช้ (ต้องทำ 2 ขั้น)

ระบบใช้ **allowlist** — คนที่ไม่อยู่ในรายชื่อจะสมัครได้แต่**ไม่เห็นข้อมูลอะไรเลย**
(ไม่มี profile → `app_role()` เป็น NULL → RLS ปฏิเสธทุกตาราง)

**ขั้นที่ 1** เพิ่มอีเมลลงรายชื่อที่อนุมัติ — ทำในแอปได้เลยที่ **ตั้งค่า → ผู้ใช้**
(หรือถ้าถนัด SQL ก็ insert ลง `public.allowed_users` ตรงๆ)

**ขั้นที่ 2** สร้าง user ใน Dashboard → **Authentication → Users → Add user**
ด้วยอีเมลเดียวกัน — profile และ role จะถูกสร้างให้อัตโนมัติ

หน้าตั้งค่าจะบอกด้วยว่าใคร "สมัครแล้ว" / "ยังไม่ได้สมัคร"

> ลำดับสำคัญ: ถ้าสร้าง user ก่อนใส่ allowlist จะไม่ได้ profile
> แก้โดยเพิ่มลง `allowed_users` แล้วลบ user ออกสร้างใหม่

**ทำไมต้องมี allowlist:** ถ้าเปิด self-signup ไว้ (ค่า default ของ Supabase)
ใครที่เจอ URL ก็สมัครเองได้ ของเดิมจะได้ role `staff` ทันที = เห็นข้อมูลลูกค้า 996 คน
พร้อมเบอร์โทร allowlist ปิดช่องนี้ที่ระดับฐานข้อมูล ไม่ต้องพึ่งการตั้งค่าใน Dashboard

## Business Logic ที่อยู่ในฐานข้อมูลแล้ว

- **เลขที่ใบเสร็จ** `SK-YYYYMMDD-NNN` — สร้างอัตโนมัติผ่าน trigger บน `sales`
  รีเซ็ตทุกวัน และกันเลขซ้ำเมื่อพนักงานหลายคนบันทึกพร้อมกัน (atomic upsert)
- **ยอด Credit สมาชิก** — view `member_balances` คำนวณ credit/bonus คงเหลือ
  โดยไม่นับ topup ที่หมดอายุแล้ว
- **ประกันมือ 500 บาท/วัน** — `MAX(sum(commission), 500)` ในหน้าค่ามือ
  อ่านค่าขั้นต่ำจาก `settings.min_commission_guarantee`
  **สำคัญ:** ประกันใช้เฉพาะวันที่หมอเข้างานจริง (มีอย่างน้อย 1 เซสชัน)
  หมอที่ไม่ได้เข้างานจะไม่ได้ประกัน
- **เวลาไทย** — `src/lib/datetime.ts` คำนวณ "วันนี้" จาก `Asia/Bangkok` เสมอ
  เพราะ server รันที่ UTC ถ้าใช้ `current_date` ตรงๆ ยอดขายหลัง 00:00 UTC (07:00 ไทย)
  จะไปลงผิดวัน

## กฎบัญชีที่ต้องรู้ (สำคัญ — เคยพลาดมาแล้ว)

**1. Bonus รวมอยู่ใน Credit แล้ว ไม่ใช่บวกเพิ่ม**
Silver จ่าย 5,000 → ใช้ได้ **6,000** (ในนั้นเป็นโบนัส 1,000) ไม่ใช่ 7,000
ยืนยันจาก Member Ledger เดิม: Credit ออกไป 318,000 − ใช้แล้ว 209,410 = คงเหลือ 108,590
ถ้าบวกโบนัสซ้ำ สมาชิก 44 คนจะได้เครดิตเกินรวม 53,000 บาท

**2. รายจ่ายหมวด `HR / payroll` คือค่ามือที่จ่ายจริง — ห้ามหักซ้ำ**
หน้ารายงานคำนวณค่ามือจากยอดขายอยู่แล้ว ถ้าเอารายจ่ายหมวดนี้มาหักอีกจะนับซ้ำ
ตัวอย่าง มิ.ย. 69: กำไรจริง +113,144 แต่ถ้านับซ้ำจะกลายเป็น −38,106

**3. ค่ามือคิดประกันรายวันต่อคน** ไม่ใช่รวมทั้งเดือนแล้วเทียบทีเดียว
ตรรกะนี้อยู่ใน view `v_therapist_daily` ที่เดียว ทุกหน้าต้องดึงจากที่นั่น
ห้ามคำนวณเอง — บั๊กเรื่องเงิน 4 จุดที่ผ่านมาเกิดจากการคำนวณซ้ำหลายที่

**ข้อจำกัดที่รู้อยู่:** ประกันใช้กับวันที่มีอย่างน้อย 1 เซสชันเท่านั้น
หมอที่มาทำงานแต่ไม่มีลูกค้าเลยจะยังไม่ได้ประกัน (เจอ 1 ครั้งใน 5 เดือน)
ต้องเพิ่มวิธีบันทึกการเข้างานในเฟสถัดไป

**4. ตรวจตัวเลขก่อนแก้สูตรทุกครั้ง** — รัน `supabase/reconciliation.sql`
ต้อง PASS ครบ 21 ข้อ ถ้ามี FAIL แปลว่าสูตรเพี้ยน

**5. ต้นเดือนกำไรดูสูงเกินจริง** เพราะค่าเช่าและเงินเดือนบันทึกตอนสิ้นเดือน
หน้า `/finance` มีแถบเตือนอัตโนมัติเมื่อต้นทุนคงที่ต่ำกว่าครึ่งของค่าเฉลี่ยย้อนหลัง
อย่าตัดสินใจจากตัวเลขเดือนที่ยังไม่ครบ

**6. ชื่อโปรโมชั่นรวมยอดผ่านตาราง `promotion_aliases` เท่านั้น**
`coupon_promo` เป็นข้อความพิมพ์มือ — `Happy Hours` เคยแตกเป็น 8 แบบจนรายงานบอกว่าใช้ 38 ครั้ง
ทั้งที่จริง 89 ครั้ง ทุกการนับโปรฯ ต้อง join ผ่าน `public.promo_key(coupon_promo)`
ห้ามใช้ `group by coupon_promo` ตรงๆ · ข้อความแบบใหม่ที่ยังไม่จับคู่จะโผล่ในแท็บ
"โปรฯ" หน้าตั้งค่า ควรเข้าไปเคลียร์เดือนละครั้ง

**7. ยอดขาย Gowabi และ KOL ไม่มีรายรับบันทึกไว้เลย**
ทั้ง 64 รายการของ Gowabi และ 25 รายการของ KOL มี `net_amount = 0` ทุกรายการ
(รวมรายการล่าสุด 18 ก.ค.) มูลค่าตั๋วรวม ฿44,700 และ ฿19,450 ตามลำดับ
แปลว่ากำไรที่หน้า `/finance` แสดง **ต่ำกว่าความจริง** เท่ากับเงินที่ Gowabi โอนมาจริง
เพราะค่ามือหมอถูกจ่ายตามปกติแต่ฝั่งรายรับเป็นศูนย์
หน้า `/insights/promotions` จึงแสดงว่า "ไม่ได้บันทึก" แทนเลข 0 — ยังไม่ได้แก้ที่ต้นเหตุ

**8. สูตรเงินของการขายอยู่ที่ `src/lib/sale-math.ts` ที่เดียว**
ทั้ง `createSale` และ `updateSale` ต้องเรียก `computeSaleAmounts()` ห้ามคำนวณเอง
ถ้าเขียนสูตรสองที่ วันหนึ่ง "บันทึกใหม่" กับ "แก้ของเดิม" จะให้ตัวเลขต่างกันโดยไม่มีใครรู้

**การแก้และการลบรายการขายจำกัดเฉพาะเดือนปัจจุบัน**
`updateSale` และ `deleteSale` ปฏิเสธรายการที่ `sale_date` อยู่นอกเดือนปัจจุบัน
และหน้า `/today` ซ่อนปุ่มแก้/ลบเมื่อช่วงวันที่เลือกออกนอกเดือนนี้
เดือนที่ปิดงบไปแล้วจึงขยับไม่ได้ — รายงานที่ส่งออกไปแล้วจะตรงกับฐานข้อมูลเสมอ
